### Key Components

| Component     | Role                                          | Examples                                         |
| :------------ | :-------------------------------------------- | :----------------------------------------------- |
| **Host**      | The application that runs the MCP client      | Claude Desktop, ChatGPT, Gemini, Cursor, VS Code |
| **Client**    | Connects to servers, routes requests          | Built into host applications                     |
| **Server**    | Exposes tools, resources, and prompts         | `@modelcontextprotocol/server-filesystem`        |
| **Transport** | Communication layer between client and server | stdio (local), Streamable HTTP (remote)          |

### Transport Options

MCP supports two primary transport mechanisms:

| Transport           | Use Case                     | How It Works                                             |
| :------------------ | :--------------------------- | :------------------------------------------------------- |
| **stdio**           | Local development, CLI tools | Server runs as subprocess, communicates via stdin/stdout |
| **Streamable HTTP** | Remote servers, production   | Single HTTP endpoint for bidirectional messaging         |

<Callout type="info">
  **Streamable HTTP (March 2025):** This transport replaced the older SSE
  (Server-Sent Events) approach. It uses a single HTTP endpoint for all
  communication, simplifying deployment and enabling better scalability. SSE is
  now deprecated—use Streamable HTTP for all new remote servers.
</Callout>

## 3.3 The Three Primitives

MCP servers can expose three types of capabilities:

### 1. Resources (Read-Only Data)

Resources are passive data that the LLM can read. Think of them as GET requests.

```python
# Conceptual example - what a resource looks like
resource = {
    "uri": "file:///home/user/documents/report.pdf",
    "name": "Q4 Report",
    "description": "Quarterly financial report",
    "mimeType": "application/pdf"
}
```

**Use cases:**

- File contents
- Database schemas
- Log files
- Configuration data
- Documentation

### 2. Tools (Executable Functions)

Tools are active functions that perform actions. Think of them as POST requests.

```python
# Conceptual example - what a tool definition looks like
tool = {
    "name": "query_database",
    "description": "Execute a SQL query against the database",
    "inputSchema": {
        "type": "object",
        "properties": {
            "sql": {
                "type": "string",
                "description": "The SQL query to execute"
            }
        },
        "required": ["sql"]
    }
}
```

**Use cases:**

- Database queries
- API calls
- File operations
- Sending messages
- Code execution

### 3. Prompts (Reusable Templates)

Prompts are pre-defined templates for common LLM interactions.

```python
# Conceptual example - what a prompt looks like
prompt = {
    "name": "analyze_code",
    "description": "Analyze code for bugs and improvements",
    "arguments": [
        {
            "name": "code",
            "description": "The code to analyze",
            "required": True
        },
        {
            "name": "language",
            "description": "Programming language",
            "required": False
        }
    ]
}
```

**Use cases:**

- Code review templates
- Data analysis workflows
- Report generation
- Standardized queries

<Callout type="tip">
  **Most Common:** Tools are by far the most commonly used primitive. Resources
  and Prompts are useful for specific scenarios but you'll spend most of your
  time working with Tools.
</Callout>

## 3.4 Building an MCP Server (Python)

Let's build a simple MCP server that exposes tools for an e-commerce system. This demonstrates the core concepts you'll use in production.

{/* INTERACTIVE_COMPONENT: MCP Tool Builder */}

### Installation

```bash
pip install mcp
```

### Basic Server Structure

```python
"""ecommerce_server.py - A simple MCP server"""
from mcp.server import Server
from mcp.server.stdio import stdio_server
from mcp.types import Tool, TextContent
import json

# Create the server
server = Server("ecommerce-tools")

# Simulated database
CUSTOMERS = {
    "CUST001": {"name": "Alice Johnson", "email": "alice@example.com"},
    "CUST002": {"name": "Bob Smith", "email": "bob@example.com"},
}

ORDERS = {
    "ORD001": {"customer_id": "CUST001", "items": ["Widget", "Gadget"], "total": 99.99},
    "ORD002": {"customer_id": "CUST002", "items": ["Gizmo"], "total": 49.99},
}


@server.list_tools()
async def list_tools() -> list[Tool]:
    """List all available tools."""
    return [
        Tool(
            name="get_customer",
            description="Get customer information by ID",
            inputSchema={
                "type": "object",
                "properties": {
                    "customer_id": {
                        "type": "string",
                        "description": "The customer ID (e.g., CUST001)"
                    }
                },
                "required": ["customer_id"]
            }
        ),
        Tool(
            name="get_orders",
            description="Get all orders for a customer",
            inputSchema={
                "type": "object",
                "properties": {
                    "customer_id": {
                        "type": "string",
                        "description": "The customer ID"
                    }
                },
                "required": ["customer_id"]
            }
        ),
    ]


@server.call_tool()
async def call_tool(name: str, arguments: dict) -> list[TextContent]:
    """Handle tool calls."""
    if name == "get_customer":
        customer_id = arguments["customer_id"]
        customer = CUSTOMERS.get(customer_id)
        if customer:
            return [TextContent(type="text", text=json.dumps(customer))]
        return [TextContent(type="text", text=f"Customer {customer_id} not found")]

    elif name == "get_orders":
        customer_id = arguments["customer_id"]
        customer_orders = [
            {"order_id": oid, **order}
            for oid, order in ORDERS.items()
            if order["customer_id"] == customer_id
        ]
        return [TextContent(type="text", text=json.dumps(customer_orders))]

    return [TextContent(type="text", text=f"Unknown tool: {name}")]


async def main():
    """Run the server."""
    async with stdio_server() as (read_stream, write_stream):
        await server.run(read_stream, write_stream)


if __name__ == "__main__":
    import asyncio
    asyncio.run(main())
```

<Callout type="info">
**Transport: stdio vs Streamable HTTP**

This example uses `stdio` (standard input/output) transport, which is ideal for local development and testing. For production deployments, use **Streamable HTTP** transport (introduced in March 2025), which provides bidirectional communication through a single HTTP endpoint. The older SSE transport is now deprecated.

</Callout>

## 3.5 Using FastMCP (Simplified API)

The `mcp` package includes `FastMCP`, a higher-level API that simplifies server creation:

```python
"""ecommerce_fastmcp.py - Using FastMCP for cleaner code"""
from mcp.server.fastmcp import FastMCP

# Create server with FastMCP
mcp = FastMCP("ecommerce-tools")

# Simulated data
CUSTOMERS = {
    "CUST001": {"name": "Alice Johnson", "email": "alice@example.com"},
    "CUST002": {"name": "Bob Smith", "email": "bob@example.com"},
}


@mcp.tool()
def get_customer(customer_id: str) -> dict:
    """
    Get customer information by ID.

    Args:
        customer_id: The customer ID (e.g., CUST001)

    Returns:
        Customer information including name and email
    """
    customer = CUSTOMERS.get(customer_id)
    if customer:
        return customer
    return {"error": f"Customer {customer_id} not found"}


@mcp.tool()
def search_customers(name_query: str) -> list[dict]:
    """
    Search for customers by name.

    Args:
        name_query: Partial name to search for

    Returns:
        List of matching customers
    """
    results = []
    for cid, customer in CUSTOMERS.items():
        if name_query.lower() in customer["name"].lower():
            results.append({"id": cid, **customer})
    return results


if __name__ == "__main__":
    mcp.run(transport="stdio")
```

<Callout type="tip">
**FastMCP Magic:** Notice how the `@mcp.tool()` decorator automatically:
- Extracts the function name as the tool name
- Uses the docstring as the description
- Generates the input schema from type hints
- Handles serialization of return values

This is the recommended approach for most use cases.

</Callout>

## 3.8 Elicitation: Interactive Workflows

One of the most powerful features added in 2025 is **Elicitation**—the ability for MCP servers to request additional information from users mid-execution. This enables truly interactive workflows.

### How Elicitation Works

Instead of failing when information is missing, a server can pause and ask the user:

<Mermaid
  chart={`
sequenceDiagram
    participant User
    participant Client as MCP Client
    participant Server as MCP Server
    
    User->>Client: "Book a flight to Paris"
    Client->>Server: call_tool("book_flight", {destination: "Paris"})

    Client->>User: "Flight booked for March 15-22"
`}
/>

### Elicitation Modes

MCP supports two elicitation modes:

| Mode     | Use Case                   | How It Works                                     |
| :------- | :------------------------- | :----------------------------------------------- |
| **Form** | Structured data collection | Server sends JSON Schema, client renders form    |
| **URL**  | OAuth flows, external auth | Server sends URL, user completes flow in browser |

### Form Mode Example

```python
# Server-side: requesting user information
@mcp.tool()
async def book_appointment(service: str) -> dict:
    """Book an appointment for a service."""
    # Request additional info via elicitation
    user_info = await mcp.elicit(
        message="Please provide your contact details",
        schema={
            "type": "object",
            "properties": {
                "name": {"type": "string", "description": "Your full name"},
                "email": {"type": "string", "format": "email"},
                "preferred_date": {"type": "string", "format": "date"},
                "notes": {"type": "string", "description": "Any special requests"}
            },
            "required": ["name", "email", "preferred_date"]
        }
    )

    # Now we have the user's info
    return {
        "status": "booked",
        "service": service,
        "customer": user_info["name"],
        "date": user_info["preferred_date"]
    }
```

### URL Mode for OAuth

URL elicitation is essential for secure authentication flows:

```python
@mcp.tool()
async def connect_github() -> dict:
    """Connect your GitHub account."""
    # Redirect user to OAuth flow
    auth_result = await mcp.elicit(
        mode="url",
        message="Please authorize access to your GitHub account",
        url="https://github.com/login/oauth/authorize?client_id=..."
    )

    # User completed OAuth, we have the token
    return {"status": "connected", "username": auth_result["username"]}
```

<Callout type="tip">
**When to Use Elicitation:**
- Collecting missing required information
- OAuth/authentication flows
- User confirmation before destructive actions
- Multi-step wizards within a single tool call

Elicitation keeps the user in control while enabling richer interactions.

</Callout>

### Key Security Features

| Feature                 | Purpose                                          |
| :---------------------- | :----------------------------------------------- |
| **Mandatory PKCE**      | Prevents authorization code interception attacks |
| **OAuth 2.1 Base**      | Modern security defaults, no implicit flow       |
| **Resource Indicators** | Specify which resources a token can access       |
| **Token Binding**       | Tokens tied to specific client instances         |

### Authorization Flow

```

│  1. Discovers server's authorization endpoint            │
│  2. Generates PKCE code_verifier and code_challenge      │
│  3. Redirects user to authorization server               │
└─────────────────────────────────────────────────────────┘
                           │
                           ▼
```

### Server-Side Authorization

```python
from mcp.server.fastmcp import FastMCP
from mcp.server.auth import OAuth2Config

mcp = FastMCP(
    "secure-server",
    auth=OAuth2Config(
        issuer="https://auth.example.com",
        audience="https://api.example.com",
        scopes=["read:data", "write:data"]
    )
)

@mcp.tool()
async def get_sensitive_data(query: str) -> dict:
    """Access sensitive data (requires authentication)."""
    # Token is automatically validated by the framework
    # Access user info from the request context
    user = mcp.get_current_user()

    # Check scopes
    if "read:data" not in user.scopes:
        return {"error": "Insufficient permissions"}

    return {"data": f"Sensitive results for {query}"}
```

<Callout type="warning">
  **Security Best Practices:** - Always use HTTPS for remote MCP servers -
  Implement proper scope validation - Use short-lived access tokens with refresh
  tokens - Log all tool invocations for audit trails - Consider rate limiting to
  prevent abuse
</Callout>

## 3.10 Recent Protocol Updates (November 2025)

The MCP specification continues to evolve. The November 2025 release introduced several important features for production deployments:

### Asynchronous Operations (Tasks)

Long-running operations like report generation or data analysis can now run asynchronously:

```python
# Conceptual example - async task pattern
@mcp.tool()
async def generate_report(data_source: str) -> dict:
    """
    Generate a comprehensive report (may take several minutes).
    Returns a task ID for polling.
    """
    task_id = await start_background_task(data_source)
    return {"task_id": task_id, "status": "processing"}

@mcp.tool()
async def get_task_status(task_id: str) -> dict:
    """Check the status of a long-running task."""
    return await check_task(task_id)
```

### Stateless Mode

Servers can now operate in stateless mode, enabling horizontal scaling and serverless deployments:

```python
# Stateless server configuration
mcp = FastMCP("stateless-server", stateless=True)
```

### Server Identity

Servers can now declare their identity, enabling better security and audit trails:

```python
server = Server(
    "my-server",
    identity={
        "name": "Production Database Server",
        "version": "1.2.0",
        "vendor": "MyCompany"
    }
)
```

### Client ID Metadata Documents

Enterprise deployments can now use metadata documents to describe client capabilities and requirements, improving interoperability in complex environments.

<Callout type="info">
  **Specification Versions:** MCP uses dated specification versions (e.g.,
  `2025-11-25`). When building production systems, specify the version you're
  targeting to ensure compatibility. Key versions: March 2025 (Streamable HTTP),
  June 2025 (OAuth 2.1, Elicitation), November 2025 (Tasks, Stateless mode).
</Callout>

## 3.12 Security Considerations

MCP provides a security boundary between your agent and external systems:

<Callout type="warning">
  **Security Principles:** User Consent (MCP clients should get user approval
  before executing tools), Least Privilege (servers should expose only necessary
  capabilities), Input Validation (always validate tool inputs on the server
  side), Audit Logging (log all tool calls for security review), Sandboxing (run
  servers with minimal permissions), and OAuth 2.1 (use proper authentication
  for sensitive operations).
</Callout>

### Example: Safe Tool Design

{/* IMAGE_PLACEHOLDER: Create a code security visualization showing input validation flow. Show a funnel/filter diagram: Top: "User Input" (SQL query) → Middle: "Validation Layers" (3 filters: 1. Check for SELECT only, 2. Block dangerous keywords, 3. Sanitize input) → Bottom: "Safe Execution" (database with shield icon). Use red X marks for blocked queries and green checkmarks for safe queries. Include example queries flowing through the system with their validation results. Style: security-focused diagram with shields, locks, and filter icons. Use red for dangerous patterns, green for safe execution, yellow for validation steps. Make it educational and clear about security best practices. */}

```python
@mcp.tool()
def query_database(sql: str) -> dict:
    """
    Execute a READ-ONLY SQL query.

    Args:
        sql: SELECT query to execute (no modifications allowed)
    """
    # Validate: only allow SELECT statements
    if not sql.strip().upper().startswith("SELECT"):
        return {"error": "Only SELECT queries are allowed"}

    # Validate: prevent dangerous patterns
    dangerous_patterns = ["DROP", "DELETE", "UPDATE", "INSERT", "TRUNCATE"]
    for pattern in dangerous_patterns:
        if pattern in sql.upper():
            return {"error": f"Query contains forbidden keyword: {pattern}"}

    # Execute safely
    try:
        result = db.execute(sql)
        return {"data": result, "row_count": len(result)}
    except Exception as e:
        return {"error": str(e)}
```

## 3.13 Advanced Patterns: Optimization & Deployment

As your MCP usage scales, you'll need advanced patterns for management and debugging.

### Master-MCP: The Proxy Pattern

In enterprise environments, connecting every agent directly to every server is unmanageable. The **Master-MCP** (or MCP Proxy) pattern introduces a central gateway:

<Mermaid
  chart={`
graph LR
    Agent[🤖 Agent] --> Proxy[🛡️ Master-MCP Proxy]
    Proxy --> DB[🗄️ Database]
    Proxy --> API[🌐 External API]
    Proxy --> Int[🔐 Internal Tool]
    
    style Proxy fill:#f9f,stroke:#333
`}
/>

**Key Benefits:**

1.  **Parameter Hiding**: The proxy can inject secrets (API keys, customer IDs) so the LLM never sees them.
2.  **Adjustable Descriptions**: Dynamically rewrite tool descriptions based on the user's role or context.
3.  **Access Control**: Enforce policy checks at a single choke point.

### Debugging with `mcp-cli`

For testing servers without spinning up a full agent, use the **mcp-cli** tool (by Phil Schmid):

```bash
# Install
curl -fSSL https://raw.githubusercontent.com/philschmid/mcp-cli/main/install.sh | bash

# List all tools on a server
mcp-cli list --server usage-mcp

# Inspect a specific tool schema
mcp-cli inspect --server usage-mcp --tool get-usage

# Call a tool directly
mcp-cli call --server usage-mcp --tool get-usage --args '{"customer_id": "123"}'
```

This is invaluable for debugging server implementations before integrating them into your agent graph.
