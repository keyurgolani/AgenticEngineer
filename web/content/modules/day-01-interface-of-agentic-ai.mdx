## 1.2 Why Pipelines Fail

In traditional software, we build **Pipelines** (or DAGs - Directed Acyclic Graphs). Data flows in one direction:

```
Input A → Function B → Function C → Output D
```

<ConceptVisual
  image="/images/day_01_02_pipeline_vs_loop_1768961505506.png"
  caption="Linear Pipeline vs. Agentic Loop: Pipelines break when they hit errors. Loops perceive constraints and adapt."
  alt="Comparison of a linear pipeline failing vs an agentic loop adapting"
/>

This is <Glossary term="Deterministic" def="Always producing the same output for the same input. No randomness or variation." />. Run it 100 times, get the same result 100 times. This predictability is a feature—until you need to handle uncertainty.

<ConceptIntro
  title="The Problem with Linear Pipelines"
  analogy="Imagine you're following a recipe that says 'bake for 30 minutes.' But what if your oven runs hot? A linear recipe can't adapt—it just follows the steps. A good chef, however, checks the food, adjusts the temperature, and maybe bakes for 25 minutes instead. Agents need to work like chefs, not recipes."
  technicalDef="DAGs (Directed Acyclic Graphs) process data in one direction with no cycles. They cannot handle runtime uncertainty, retry failed operations, or adapt based on intermediate results. Agents require cyclical graphs that can loop back based on observations."
  whyItMatters="Real-world tasks are messy. APIs fail, LLMs make mistakes, and requirements change mid-task. Agents must handle this uncertainty gracefully through iteration and recovery."
/>

Agents live in a <Glossary term="Probabilistic" def="Involving chance or variation; not deterministic. The same input might produce different outputs." /> world.

If you ask an agent to "Fix the bug in main.py", it might:

1. Read the file
2. Analyze the error
3. Try a fix
4. Run the tests
5. **Fail** ❌
6. Read the new error message
7. Try a different fix
8. **Succeed** ✅

A linear pipeline cannot handle step 5. It would just crash or return an error. An **Agentic Loop** can perceive the failure, reason about what went wrong, and try again.

<RealWorldExample

  implementation="The agent: (1) Reads the test file and error message, (2) Hypothesizes the cause based on the stack trace, (3) Makes a code change, (4) Runs the test, (5) If it fails, reads the new error and adjusts its hypothesis, (6) Repeats until the test passes or it determines it needs human help."
  takeaway="This requires a loop, not a pipeline. The agent must observe results and adjust its approach—something impossible in a linear DAG. This is the fundamental shift from traditional programming to agentic systems."

## 1.3 The ReAct Pattern: How Agents Think

The core transformation in this course is moving from **Chains** (Linear) to **Loops** (Cyclical).

The industry-standard pattern for this is called **ReAct** (Reason + Act), introduced in a [2022 research paper by Yao et al.](https://arxiv.org/abs/2210.03629) that fundamentally changed how we build agents. The paper demonstrated that interleaving reasoning traces with actions significantly improves task performance compared to reasoning-only or action-only approaches:

<Mermaid
  chart={`
graph TD
    Start([User Request]) --> Reason
    Reason[1. Reason<br/>Think about what to do] --> Act{2. Act<br/>Execute a tool}
    Act -->|"Tool returns result"| Observe[3. Observe<br/>See the result]
    Observe --> Reason
    Reason -->|"Task complete"| End([Final Answer])

    style Reason fill:#f9f,stroke:#333,stroke-width:2px
    style Act fill:#bbf,stroke:#333,stroke-width:2px
    style Observe fill:#bfb,stroke:#333,stroke-width:2px

`}
/>

### The Three Steps of ReAct

<ConceptVisual
  image="/images/day_01_03_react_loop_interactive_1768961518105.png"
  caption="The ReAct Pattern: Reason -> Act -> Observe. This continuous cycle enables agents to tackle complex, multi-step tasks."
  alt="Circular diagram showing the Reason, Act, Observe loop"
/>

| Step           | What Happens                                     | Example                                                                |
| :------------- | :----------------------------------------------- | :--------------------------------------------------------------------- |
| **1. Reason**  | Think about the current state and plan next step | "The user wants flight options. I should search for flights to Tokyo." |
| **2. Act**     | Execute a tool or generate a response            | Call `search_flights(destination="Tokyo", date="2024-03-15")`          |
| **3. Observe** | See the result of the action                     | Tool returns: 3 flights found, cheapest is $450                        |

Then the loop continues: Reason ("I found options, I should present them to the user") → Act (format and display results) → Observe (user says "book the $450 one") → Reason → Act → ...

<Callout type="tip">
  **Mental Model:** Think of the agent as a thoughtful assistant who narrates
  their thinking. "Let me search for that... okay, I found 3 options... the
  cheapest is $450... I should ask if they want to book it." This explicit
  reasoning helps the agent stay on track and makes debugging easier.
</Callout>

### ReAct in Practice

Here's what a ReAct trace looks like in practice:

<ConceptVisual
  image="/images/day_01_04_react_trace_visualizer_1768961537309.png"
  caption="Visualizing Thought: Explicit reasoning traces help us understand how the agent arrived at its decision."
  alt="UI mockup of a ReAct trace with thought, action, observation steps"
/>

```
User: What's the weather in Tokyo and should I bring an umbrella?

Thought: I need to check the current weather in Tokyo to answer this question.
Action: get_weather(location="Tokyo")
Observation: {"temp": 18, "condition": "light rain", "humidity": 75}

Thought: It's currently raining in Tokyo with light rain. The user should
definitely bring an umbrella. Let me provide a helpful response.
Action: respond_to_user
Response: It's currently 18°C in Tokyo with light rain and 75% humidity.
Yes, definitely bring an umbrella! ☔
```

<DeepDive title="Why Explicit Reasoning Matters">

The key insight from the ReAct paper is that **explicit reasoning traces improve task performance**. When the model "thinks out loud":

1. **Better planning**: The model can break complex tasks into steps
2. **Error recovery**: When something fails, the reasoning trace helps identify what went wrong
3. **Debuggability**: You can see exactly why the agent made each decision
4. **Grounding**: Reasoning traces help the model stay focused on the actual task

Without explicit reasoning, models tend to jump to conclusions or get confused on multi-step tasks. ReAct forces a more deliberate, step-by-step approach.

</DeepDive>

<Callout type="info">
  **Historical Note:** ReAct builds on the OODA Loop (Observe, Orient, Decide,
  Act) from military strategy, but adapts it for AI systems. The key innovation
  was showing that interleaving reasoning with actions outperforms both
  reasoning-only and action-only approaches. Related patterns include
  **Reflexion** (adding self-reflection on past attempts) and
  **Plan-and-Execute** (separating planning from execution).
</Callout>

<DeepDive title="When to Use Each Pattern">

**ReAct** remains the default choice for most tasks. Use it when:

- Tasks require real-time adaptation
- You need visibility into agent reasoning
- The path to completion isn't known in advance

**Reflexion** adds a self-critique step after each attempt:

```
Attempt → Result → Reflection → Improved Attempt
```

Use when agents repeatedly make similar mistakes or when learning from failure is valuable.

**Plan-and-Execute** separates planning from execution:

```
1. Create complete plan
2. Execute each step
3. Re-plan if needed
```

Use for well-defined tasks where upfront planning reduces errors (e.g., code refactoring, data migrations).

**Multi-Agent** systems use specialized agents that collaborate:

```
Coordinator → [Researcher, Coder, Reviewer] → Final Output
```

Use when tasks span multiple domains or require different "personalities" (e.g., one agent writes code, another reviews it).

We'll implement several of these patterns in later modules, culminating in multi-agent systems in Month 2 (Days 31-60).

</DeepDive>

## 1.4 Tool Calling: How Agents Take Action

The magic that enables agents to act in the world is **tool calling** (also called function calling). This is a capability built into modern LLMs that lets them request execution of external functions.

<ConceptVisual
  image="/images/day_01_05_tool_calling_sequence_1768961568311.png"
  caption="Tool Calling Flow: The LLM generates a structured request, and the Agent executes it using the Tool. The LLM never touches the tool directly."
  alt="Sequence diagram showing flow between User, Agent, LLM, and Tool"
/>

<ConceptIntro
  title="Tool Calling"
  analogy="Imagine you're a manager who can't directly access the company database, but you can write a request slip that says 'Please look up customer #12345's order history.' You hand the slip to an assistant who executes the query and brings back the results. Tool calling works the same way—the LLM writes a structured request, your code executes it, and the results come back to the LLM."
  technicalDef="Tool calling is an API feature where you define available functions (with names, descriptions, and parameter schemas), and the LLM can output structured JSON to invoke them. The LLM doesn't execute the tools—it generates the parameters, and your code handles execution and returns results."
  whyItMatters="Tool calling is what transforms an LLM from a text generator into an agent. Without it, the LLM can only talk about doing things. With it, the LLM can actually do things—search the web, query databases, send emails, execute code."
/>

<Callout type="important">
  **Critical Understanding:** The LLM never executes tools directly. It only
  *requests* that tools be executed by outputting structured JSON. Your
  application code is responsible for actually running the tool and returning
  results. This separation is important for security and control.
</Callout>

### Defining Tools

When you call an LLM API with tools, you provide schemas that describe what each tool does. Here's the standard format used by OpenAI and most providers:

<ConceptVisual
  image="/images/day_01_06_tool_schema_visualizer_1768961587471.png"
  caption="Tool Schemas: The 'prompt' for tools. The LLM uses the description to understand purpose and parameters to format requests."
  alt="Split view showing JSON schema and LLM interpretation"
/>

```python
tools = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "Get the current weather for a location. Returns temperature, conditions, and humidity.",
            "parameters": {
                "type": "object",
                "properties": {
                    "location": {
                        "type": "string",
                        "description": "City name, e.g., 'Paris, France' or 'Tokyo, Japan'"
                    },
                    "units": {
                        "type": "string",
                        "enum": ["celsius", "fahrenheit"],
                        "default": "celsius",
                        "description": "Temperature units to return"
                    }
                },
                "required": ["location"]
            }
        }
    }
]
```

The LLM reads these descriptions and decides when and how to use each tool. **Good tool descriptions are crucial**—they're essentially prompts that teach the LLM what each tool does and when to use it.

### Parallel Tool Calling

Modern LLMs can request multiple tools in a single response. For example, if you ask "What's the weather in Paris and Tokyo?", the model might return:

<ConceptVisual
  image="/images/day_01_07_sequential_vs_parallel_tools_1768961603811.png"
  caption="Optimization: Parallel tool calling significantly reduces total latency for independent tasks."
  alt="Timeline comparison of sequential vs parallel tool execution"
/>

```json
{
  "tool_calls": [
    { "name": "get_weather", "arguments": { "location": "Paris" } },
    { "name": "get_weather", "arguments": { "location": "Tokyo" } }
  ]
}
```

Your agent can execute these in parallel for better performance. This is especially useful for tasks that require gathering information from multiple sources.

<Callout type="tip">
  **Performance Tip:** When building agents, look for opportunities to batch
  independent tool calls. Parallel execution can significantly reduce latency
  for multi-step tasks.
</Callout>

<Callout type="info">
  **Structured Outputs:** Modern LLM APIs (OpenAI, Anthropic) support "strict"
  mode for tool calling, which guarantees the output matches your JSON schema
  exactly. This eliminates parsing errors and makes agents more reliable. Always
  enable strict mode in production.
</Callout>

## 1.4.1 Tool Calling Across Providers

Different AI providers have evolved their own approaches to tool calling. Understanding these differences helps you build portable agents and choose the right platform for your use case.

### OpenAI: Responses API & Agents SDK

In March 2025, OpenAI released the **Responses API** and **Agents SDK**, representing a major evolution in their agent infrastructure:

- **Responses API**: Combines Chat Completions simplicity with Assistants API tool capabilities
- **Built-in tools**: Web search, file search, code interpreter, and computer use
- **MCP support**: Added in May 2025, enabling connection to any MCP server
- **Structured Outputs**: Setting `strict: true` guarantees JSON schema compliance

```python
from openai import OpenAI

client = OpenAI()

# Using the Responses API with built-in tools
response = client.responses.create(
    model="gpt-4.1",
    input="What's the latest news about AI agents?",
    tools=[{"type": "web_search"}]  # Built-in web search
)
```

### Anthropic: Advanced Tool Use

Anthropic's Claude models excel at complex tool orchestration:

- **Advanced Tool Use** (November 2025): Handles 100+ tools without context pollution
- **Computer Use**: Claude can control desktop applications via screenshots and mouse/keyboard
- **Claude Agent SDK**: Production-ready framework for building autonomous agents
- **Prompt caching**: Reduces latency for stable tool definitions

```python
import anthropic

client = anthropic.Anthropic()

# Claude with tool use
response = client.messages.create(
    model="claude-sonnet-4-20250514",
    max_tokens=1024,
    tools=[{
        "name": "get_weather",
        "description": "Get current weather for a location",
        "input_schema": {
            "type": "object",
            "properties": {
                "location": {"type": "string"}
            },
            "required": ["location"]
        }
    }],
    messages=[{"role": "user", "content": "What's the weather in Tokyo?"}]
)
```

### Google: Gemini Function Calling

Google's Gemini models offer deep integration with Google services:

- **Gemini Agent**: Multi-step task execution with Calendar, Gmail, and Drive integration
- **Agentic browsing**: Can work across multiple browser tabs
- **Let Google Call**: AI can phone businesses to gather information
- **Native MCP support**: Added at Google I/O 2025

<Callout type="info">
  **Choosing a Provider:** For most agent tasks, all major providers work well.
  Choose based on: existing infrastructure (Google Cloud → Gemini), specific
  capabilities (computer use → Claude), or ecosystem (OpenAI if using their
  other tools). MCP support means your tools work across all of them.
</Callout>

## 1.5 Introduction to MCP

How does the Brain talk to the Hands? We need a standard interface. Enter **MCP**.

<ConceptVisual
  image="/images/day_01_08_mcp_ecosystem_hub_1768961619997.png"
  caption="The MCP Standard: A universal connector linking any AI model to any data source."
  alt="Ecosystem diagram showing MCP as a hub connecting AI providers and tools"
/>

<ConceptIntro
  title="Model Context Protocol (MCP)"
  analogy="Before USB, every device had its own connector—printers, cameras, phones all needed different cables. USB standardized this: one port, many devices. MCP does the same for AI tools. Instead of writing custom code to connect each tool to each AI system, MCP provides one standard that works everywhere."
  technicalDef="MCP (Model Context Protocol) is an open standard introduced by Anthropic in November 2024 that defines how AI systems connect to external tools and data sources. It specifies a client-server architecture where MCP Servers expose tools/resources and MCP Clients (agents) consume them via JSON-RPC. In December 2025, Anthropic donated MCP to the newly created Agentic AI Foundation (AAIF) under the Linux Foundation, co-founded with Block and OpenAI—establishing MCP as a vendor-neutral industry standard."
  whyItMatters="MCP means you can write a tool once and use it with Claude, GPT, Gemini, or any MCP-compatible agent. The ecosystem has exploded: over 10,000 public MCP servers, 97 million SDK downloads per month, and adoption by every major AI provider. It's become the de facto standard for AI data connectivity."
/>

### What MCP Provides

Instead of writing custom API wrappers for every tool, MCP provides a universal standard for:

- **Tools**: Executable functions (e.g., `list_files`, `run_query`, `send_email`)
- **Resources**: Data sources the agent can read (e.g., logs, documents, database schemas)
- **Prompts**: Reusable templates for common tasks

### How Components Work Together

1. **User sends a request** through the interface
2. **Orchestrator receives the request** and initializes state
3. **LLM reasons** about what to do (the "Reason" step)
4. **Orchestrator executes tools** based on LLM's decision (the "Act" step)
5. **Results flow back** to the orchestrator (the "Observe" step)
6. **Loop continues** until the task is complete
7. **Memory persists** important information for future interactions

  **LangGraph Preview:** In Day 03, we'll implement this architecture using
  LangGraph. The orchestrator becomes a "graph" with nodes (functions) and edges
  (control flow). State flows through the graph, and the LLM decides which path
  to take. LangGraph Platform (now called LangSmith Deployment) provides managed
  infrastructure for deploying these stateful agents at scale.
</Callout>

## 1.7 LLM API vs Agent: A Code Comparison

To make the distinction concrete, let's compare a simple LLM API call with an agent loop:

<Callout type="warning">
  **Anthropic's Key Insight:** "When building applications with LLMs, we
  recommend finding the simplest solution possible, and only increasing
  complexity when needed. This might mean not building agentic systems at all.
  Agentic systems often trade latency and cost for better task performance."
  Always ask: does this task actually need an agent, or would a simple prompt
  suffice?
</Callout>

### Raw LLM API Call (No Agency)

```python
from openai import OpenAI

client = OpenAI()

# Simple completion - no tools, no memory, no loop
response = client.chat.completions.create(
    model="gpt-4.1",
    messages=[
        {"role": "user", "content": "What's the weather in Tokyo?"}
    ]
)

print(response.choices[0].message.content)
# Output: "I don't have access to real-time weather data..."
```

The LLM can only respond with what it knows from training. It can't actually check the weather.

### Agent with Tool Calling

```python
from openai import OpenAI
import json

client = OpenAI()

# Define available tools
tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "Get current weather for a city. Returns temperature in Celsius and conditions.",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {"type": "string", "description": "City name, e.g., 'Tokyo, Japan'"}
            },
            "required": ["city"]
        }
    }
}]

def get_weather(city: str) -> dict:
    """Actual implementation that calls a weather API."""
    # In production, this would call a real weather service
    # For demo purposes, returning mock data
    return {"city": city, "temp_celsius": 22, "condition": "sunny"}

def run_agent(user_message: str) -> str:
    """Run a simple ReAct agent loop."""
    messages = [{"role": "user", "content": user_message}]

    max_iterations = 10  # Prevent infinite loops

    for _ in range(max_iterations):
        # 1. REASON: Ask LLM what to do
        response = client.chat.completions.create(
            model="gpt-4.1",
            messages=messages,
            tools=tools
        )

        assistant_message = response.choices[0].message
        messages.append(assistant_message)

        # 2. Check if we're done or need to ACT
        if not assistant_message.tool_calls:
            # No tool calls - return final response
            return assistant_message.content

        # 3. ACT: Execute each tool call
        for tool_call in assistant_message.tool_calls:
            function_name = tool_call.function.name
            arguments = json.loads(tool_call.function.arguments)

            # Execute the tool
            if function_name == "get_weather":
                result = get_weather(**arguments)
            else:
                result = {"error": f"Unknown tool: {function_name}"}

            # 4. OBSERVE: Add result to conversation
            messages.append({
                "role": "tool",
                "tool_call_id": tool_call.id,
                "content": json.dumps(result)
            })

    return "Max iterations reached without completing task."

# Run the agent
answer = run_agent("What's the weather in Tokyo?")
print(answer)
# Output: "It's currently 22°C and sunny in Tokyo!"
```

<Callout type="tip">
  **Key Difference:** The raw LLM call is a single request-response. The agent
  runs a loop that continues until the task is complete, calling tools as
  needed. This is the fundamental architectural difference between a chatbot and
  an agent.
</Callout>

<DeepDive title="When to Use Agents vs. Simpler Approaches">

Not every task needs an agent. Anthropic's research team recommends this decision framework:

**Use a simple prompt when:**

- The task is well-defined with predictable inputs
- No external data or actions are needed
- A single LLM call can produce the answer

**Use a chain/pipeline when:**

- Multiple steps are needed but the flow is predictable
- Each step's output feeds the next step
- No iteration or error recovery is required

**Use an agent when:**

- The task requires real-world actions (API calls, file operations)
- The number of steps isn't known in advance
- Error recovery and iteration are essential
- The task involves gathering information from multiple sources

**The tradeoff:** Agents provide better task performance but at the cost of higher latency (multiple LLM calls), higher cost (more tokens), and increased complexity. Start simple and add agency only when needed.

</DeepDive>

<Callout type="warning">
  **Production Note:** The code above is simplified for learning. Production
  agents need additional handling for: rate limits, timeouts, error recovery,
  logging, cost tracking, and security validation of tool inputs.
</Callout>
