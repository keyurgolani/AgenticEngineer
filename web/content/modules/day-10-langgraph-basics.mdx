### Two Ways to Build: Graph API vs Functional API

LangGraph offers two complementary approaches for building workflows:

| Approach                                    | Best For                                                         | Style                        |
| :------------------------------------------ | :--------------------------------------------------------------- | :--------------------------- |
| **Graph API** (`StateGraph`)                | Complex multi-agent systems, explicit control flow visualization | Declarative graph definition |
| **Functional API** (`@entrypoint`, `@task`) | Simpler workflows, existing codebases, rapid prototyping         | Traditional Python functions |

Both APIs use the same underlying runtime and can be mixed. We'll focus on the Graph API first (it's more explicit about what's happening), then show the Functional API alternative.

## 3.3 The 'Hello World' of Agents

Let's build a minimal graph step by step, using the modern LangGraph API.

### Step 1: Define the State

The state is the memory of our graph. We use `TypedDict` with `Annotated` types to specify how updates should be merged.

```python
from typing import TypedDict, Annotated
import operator

class AgentState(TypedDict):
    # 'operator.add' means new messages are appended, not overwritten
    messages: Annotated[list[str], operator.add]
```

<Callout type="info">
**What's `Annotated[list[str], operator.add]`?**

This tells LangGraph how to merge state updates using a **reducer**. When a node returns `{"messages": ["new message"]}`, it should _append_ to the existing list, not replace it. This is crucial for building up conversation history.

Without a reducer, each update would overwrite the previous value entirely.

### Step 2: Define the Node (The Brain)

Nodes are standard Python functions that take the **State** as input and return an **Update** to the state.

```python
def call_model(state: AgentState) -> dict:
    """The 'brain' of our agent - decides what to do."""
    # In a real agent, this would call OpenAI/Anthropic
    # For now, we simulate a simple decision
    last_message = state["messages"][-1]

    if "hello" in last_message.lower():
        return {"messages": ["World!"]}

    return {"messages": ["I don't understand."]}
```

<Callout type="tip">
  **Key Pattern:** Nodes receive the full state, but only return the *changes*
  they want to make. LangGraph handles merging these changes back into the state
  using the reducers you defined.
</Callout>

### Step 3: Build the Graph

We wire the nodes and edges together using `StateGraph`.

{/* IMAGE_PLACEHOLDER: Create a step-by-step visual guide showing the graph construction process. Show three frames: 1) Empty StateGraph being initialized with the schema, 2) Node being added (show the function being "plugged in" to the graph), 3) Edges being drawn connecting START → agent → END. Use a construction/assembly metaphor with pieces clicking together. Style: Instructional diagram with numbered steps and visual flow. */}

```python
from langgraph.graph import StateGraph, START, END

# Initialize graph with our State schema
builder = StateGraph(AgentState)

# Add our node
builder.add_node("agent", call_model)

# Define edges: START -> agent -> END
builder.add_edge(START, "agent")
builder.add_edge("agent", END)

# Compile the graph into a runnable application
app = builder.compile()
```

<Callout type="warning">
  **API Update:** In modern LangGraph, use `START` and `END` constants instead
  of `set_entry_point()`. The `START` constant represents the graph's entry
  point, and `END` represents termination.
</Callout>

### Step 4: Run It

```python
# Invoke with initial state
result = app.invoke({"messages": ["Hello there"]})
print(result["messages"])
# Output: ['Hello there', 'World!']
```

## 3.4 Complete Working Example

Here's the full code you can run locally:

```python
"""hello_agent.py - Your first LangGraph agent"""
from typing import TypedDict, Annotated
import operator
from langgraph.graph import StateGraph, START, END


class AgentState(TypedDict):
    """State schema for our simple agent."""
    messages: Annotated[list[str], operator.add]


def call_model(state: AgentState) -> dict:
    """Process the last message and generate a response."""
    last_message = state["messages"][-1]

    if "hello" in last_message.lower():
        return {"messages": ["World!"]}
    elif "bye" in last_message.lower():
        return {"messages": ["Goodbye! 👋"]}
    else:
        return {"messages": ["I don't understand that."]}


# Build the graph
builder = StateGraph(AgentState)
builder.add_node("agent", call_model)
builder.add_edge(START, "agent")
builder.add_edge("agent", END)

# Compile
app = builder.compile()

# Test it
if __name__ == "__main__":
    result = app.invoke({"messages": ["Hello there"]})
    print("Messages:", result["messages"])
    # Output: Messages: ['Hello there', 'World!']
```

## 3.6 Adding Conditional Logic (The ReAct Loop)

Now let's implement the ReAct pattern from Day 01. The agent will:

1. **Reason** about what to do
2. **Act** by calling a tool (if needed)
3. **Observe** the result
4. **Loop** back or finish

{/* IMAGE_PLACEHOLDER: Create a circular flow diagram showing the ReAct loop in action. Show four connected stages arranged in a circle: "Reason" (brain icon), "Act" (tool/wrench icon), "Observe" (eye icon), and a decision diamond "Done?" with two paths: one looping back to "Reason" and one exiting to "Finish". Add small example text bubbles at each stage showing what happens. Use arrows with motion lines to emphasize the cyclical nature. Style: Dynamic circular diagram with clear visual flow and decision point. */}

```python
from typing import TypedDict, Annotated, Literal
import operator
from langgraph.graph import StateGraph, START, END


class AgentState(TypedDict):
    """State for our ReAct agent."""
    messages: Annotated[list[str], operator.add]
    # Track whether we need to continue the loop
    needs_tool: bool


def reason(state: AgentState) -> dict:
    """The 'brain' - decides what to do based on the message."""
    last_message = state["messages"][-1].lower()

    if "search" in last_message or "find" in last_message:
        return {
            "messages": ["I'll search for that..."],
            "needs_tool": True
        }
    elif "calculate" in last_message:
        return {
            "messages": ["Let me calculate that..."],
            "needs_tool": True
        }
    else:
        return {
            "messages": ["Here's my answer based on what I know!"],
            "needs_tool": False
        }


def act(state: AgentState) -> dict:
    """Simulate using a tool."""
    # In a real agent, this would call actual tools
    return {"messages": ["[Tool Result: Found 3 relevant documents]"]}


def should_continue(state: AgentState) -> Literal["act", "__end__"]:
    """Routing function - decides which node to go to next."""
    if state.get("needs_tool", False):
        return "act"
    return END


# Build the graph
builder = StateGraph(AgentState)

# Add nodes
builder.add_node("reason", reason)
builder.add_node("act", act)

# Define flow
builder.add_edge(START, "reason")

# Conditional edge: after reasoning, check if we need to act
builder.add_conditional_edges(
    "reason",
    should_continue,
    {
        "act": "act",
        END: END
    }
)

# After acting, go back to reason (the loop!)
builder.add_edge("act", "reason")

# Compile
app = builder.compile()
```

    Reason -->|"needs_tool=False"| End([🏁 __end__])
    Act --> Reason

## 3.7 Using MessagesState (The Practical Approach)

For real chat applications, LangGraph provides a built-in `MessagesState` that handles message management with proper reducers:

```python
from langgraph.graph import StateGraph, START, END, MessagesState
from langchain_core.messages import HumanMessage, AIMessage


def chatbot(state: MessagesState) -> dict:
    """A simple chatbot node using MessagesState."""
    # MessagesState has a 'messages' key with a built-in reducer
    last_message = state["messages"][-1]

    # Generate a response (in reality, you'd call an LLM here)
    response = AIMessage(content=f"You said: {last_message.content}")

    return {"messages": [response]}


# Build graph with MessagesState
builder = StateGraph(MessagesState)
builder.add_node("chatbot", chatbot)
builder.add_edge(START, "chatbot")
builder.add_edge("chatbot", END)

app = builder.compile()

# Test with proper message types
result = app.invoke({
    "messages": [HumanMessage(content="Hello, agent!")]
})

for msg in result["messages"]:
    print(f"{msg.type}: {msg.content}")
# human: Hello, agent!
# ai: You said: Hello, agent!
```

<Callout type="tip">
**Why MessagesState?** It provides:
- Built-in `add_messages` reducer that handles message deduplication
- Proper typing for LangChain message objects
- Compatibility with LLM integrations

Use `MessagesState` for any chat-based agent.

</Callout>

## 3.8 Integrating with Real LLMs

Here's how to connect your graph to an actual LLM:

```python
from langgraph.graph import StateGraph, START, END, MessagesState
from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage, SystemMessage

# Initialize the LLM
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)


def call_llm(state: MessagesState) -> dict:
    """Call the LLM with the current messages."""
    # Add a system message for context
    system = SystemMessage(content="You are a helpful assistant.")
    messages = [system] + state["messages"]

    # Call the LLM
    response = llm.invoke(messages)

    return {"messages": [response]}


# Build the graph
builder = StateGraph(MessagesState)
builder.add_node("llm", call_llm)
builder.add_edge(START, "llm")
builder.add_edge("llm", END)

app = builder.compile()

# Use it
result = app.invoke({
    "messages": [HumanMessage(content="What's the capital of France?")]
})
print(result["messages"][-1].content)
# Paris is the capital of France.
```

<Callout type="warning">
  **API Key Required:** To run this example, set your `OPENAI_API_KEY`
  environment variable. You can also use `ChatAnthropic` from
  `langchain_anthropic` for Claude models.
</Callout>

## 3.9 Using the Prebuilt ReAct Agent

For rapid prototyping, LangGraph provides a prebuilt ReAct agent that handles the loop logic for you:

```python
from langgraph.prebuilt import create_react_agent
from langchain_openai import ChatOpenAI
from langchain_core.tools import tool

# Define tools
@tool
def search(query: str) -> str:
    """Search for information on the web."""
    # In production, this would call a real search API
    return f"Search results for: {query}"

@tool
def calculator(expression: str) -> str:
    """Evaluate a mathematical expression."""
    try:
        return str(eval(expression))
    except Exception as e:
        return f"Error: {e}"

# Create the agent
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)
agent = create_react_agent(llm, tools=[search, calculator])

# Use it
result = agent.invoke({
    "messages": [("user", "What is 25 * 4 + 10?")]
})
print(result["messages"][-1].content)
# The answer is 110.
```

<Callout type="info">
**When to use prebuilt vs. custom graphs:**
- **Prebuilt `create_react_agent`**: Great for prototyping and simple tool-calling agents
- **Custom `StateGraph`**: Use when you need custom state, complex routing, or multi-agent patterns

The prebuilt agent is essentially a pre-configured StateGraph with the ReAct pattern. Understanding how to build custom graphs (as we did above) helps you customize when needed.

</Callout>

## 3.11 Adding Persistence with Checkpointers

One of LangGraph's most powerful features is built-in persistence. Checkpointers save the graph state after each step, enabling:

- **Resumption**: Pick up where you left off after a crash
- **Human-in-the-loop**: Pause for human approval, then continue
- **Time travel**: Replay or branch from any previous state

{/* IMAGE_PLACEHOLDER: Create a timeline visualization showing checkpointing in action. Show a horizontal timeline with checkpoint markers (like save points in a video game). Illustrate three scenarios: 1) Normal execution with checkpoints being saved at each node, 2) A crash occurring and then resumption from the last checkpoint, 3) A branch point where execution splits into two paths from a checkpoint. Use icons: floppy disk for saves, lightning bolt for crash, fork symbol for branching. Style: Game-like save point aesthetic with a technical twist. */}

```python
from langgraph.checkpoint.memory import MemorySaver
from langgraph.graph import StateGraph, START, END, MessagesState

# Create a checkpointer (in-memory for development)
checkpointer = MemorySaver()

# Build your graph as usual
builder = StateGraph(MessagesState)
builder.add_node("agent", call_llm)
builder.add_edge(START, "agent")
builder.add_edge("agent", END)

# Compile WITH the checkpointer
app = builder.compile(checkpointer=checkpointer)

# Use with a thread_id to track conversation
config = {"configurable": {"thread_id": "user-123"}}

# First message
result = app.invoke(
    {"messages": [("user", "My name is Alice")]},
    config=config
)

# Later message - the agent remembers!
result = app.invoke(
    {"messages": [("user", "What's my name?")]},
    config=config
)
print(result["messages"][-1].content)
# Your name is Alice!
```

<Callout type="tip">
  **Production Checkpointers:** For production, use persistent checkpointers
  like `SqliteSaver` or `PostgresSaver` instead of `MemorySaver`. This ensures
  state survives restarts and can be shared across instances.
</Callout>

## 3.12 The Functional API (Alternative Approach)

LangGraph 1.0 introduced the **Functional API** as an alternative to the Graph API. It uses Python decorators to add LangGraph features to regular functions—no explicit graph definition required.

### When to Use the Functional API

| Use Functional API When...                 | Use Graph API When...                     |
| :----------------------------------------- | :---------------------------------------- |
| Adding LangGraph features to existing code | Building complex multi-agent systems      |
| Simpler, linear workflows                  | Need explicit visualization of flow       |
| Prefer traditional Python control flow     | Complex conditional routing               |
| Rapid prototyping                          | Team needs to understand the architecture |

### Core Primitives

The Functional API has two main decorators:

- **`@entrypoint`**: Wraps the main workflow function, enables checkpointing
- **`@task`**: Defines parallelizable units of work within an entrypoint

```python
from langgraph.func import entrypoint, task
from langgraph.checkpoint.memory import MemorySaver

@task
def analyze_data(data: str) -> str:
    """A task that can run in parallel with other tasks."""
    # Simulate analysis
    return f"Analysis of: {data}"

@task
def generate_report(analysis: str) -> str:
    """Generate a report from analysis."""
    return f"Report based on {analysis}"

@entrypoint(checkpointer=MemorySaver())
def research_workflow(topic: str) -> dict:
    """Main workflow using regular Python control flow."""
    # Tasks return futures - call .result() to get the value
    analysis = analyze_data(topic).result()

    # Regular Python conditionals work naturally
    if "urgent" in topic.lower():
        report = generate_report(analysis).result()
        return {"analysis": analysis, "report": report}

    return {"analysis": analysis}

# Use it like a regular function
result = research_workflow.invoke("AI agents")
print(result)
```

### Human-in-the-Loop with Functional API

The Functional API makes human-in-the-loop patterns particularly clean:

```python
from langgraph.func import entrypoint, task
from langgraph.types import interrupt, Command
from langgraph.checkpoint.memory import MemorySaver

@task
def write_draft(topic: str) -> str:
    """Write a draft essay."""
    return f"Draft essay about: {topic}"

@entrypoint(checkpointer=MemorySaver())
def essay_workflow(topic: str) -> dict:
    """Workflow that pauses for human review."""
    draft = write_draft(topic).result()

    # Pause and wait for human input
    approval = interrupt({
        "draft": draft,
        "action": "Please review and approve/reject"
    })

    return {
        "draft": draft,
        "approved": approval,
        "status": "published" if approval else "rejected"
    }

# Start the workflow
config = {"configurable": {"thread_id": "essay-1"}}
result = essay_workflow.invoke("LangGraph basics", config=config)
# Workflow pauses at interrupt...

# Later, resume with human input
from langgraph.types import Command
result = essay_workflow.invoke(
    Command(resume=True),  # Resume with approval
    config=config
)
```

<Callout type="info">
  **Functional API Benefits:** - No need to define nodes and edges explicitly -
  Regular Python loops and conditionals control flow - Tasks can run in parallel
  automatically - Same checkpointing and streaming as Graph API - Easier to add
  to existing codebases
</Callout>

### Creating a Subgraph

```python
from langgraph.graph import StateGraph, START, END
from typing import TypedDict, Annotated
import operator

# Define subgraph state
class ResearchState(TypedDict):
    query: str
    results: Annotated[list[str], operator.add]

def search(state: ResearchState) -> dict:
    """Search for information."""
    return {"results": [f"Found info about: {state['query']}"]}

def summarize(state: ResearchState) -> dict:
    """Summarize search results."""
    summary = f"Summary of {len(state['results'])} results"
    return {"results": [summary]}

# Build the subgraph
research_builder = StateGraph(ResearchState)
research_builder.add_node("search", search)
research_builder.add_node("summarize", summarize)
research_builder.add_edge(START, "search")
research_builder.add_edge("search", "summarize")
research_builder.add_edge("summarize", END)

research_subgraph = research_builder.compile()
```

### Using Subgraphs in a Parent Graph

```python
# Parent graph state
class AgentState(TypedDict):
    messages: Annotated[list[str], operator.add]
    research_query: str
    research_results: list[str]

def decide_action(state: AgentState) -> dict:
    """Decide what action to take."""
    last_msg = state["messages"][-1]
    if "research" in last_msg.lower():
        return {"research_query": last_msg}
    return {"messages": ["I can help with research tasks."]}

def do_research(state: AgentState) -> dict:
    """Call the research subgraph."""
    # Invoke subgraph with its expected input
    result = research_subgraph.invoke({
        "query": state["research_query"],
        "results": []
    })
    return {"research_results": result["results"]}

# Build parent graph
builder = StateGraph(AgentState)
builder.add_node("decide", decide_action)
builder.add_node("research", do_research)  # Subgraph as a node
builder.add_edge(START, "decide")
builder.add_conditional_edges(
    "decide",
    lambda s: "research" if s.get("research_query") else END,
    {"research": "research", END: END}
)
builder.add_edge("research", END)

agent = builder.compile()
```

## 3.14 The Command Primitive

The **Command** primitive combines state updates with control flow in a single return value. This is powerful for nodes that need to both update state AND decide where to go next.

```python
from langgraph.types import Command
from langgraph.graph import StateGraph, START, END

class AgentState(TypedDict):
    messages: Annotated[list[str], operator.add]
    next_action: str

def router(state: AgentState) -> Command:
    """Route to different nodes based on content."""
    last_msg = state["messages"][-1].lower()

    if "search" in last_msg:
        # Update state AND route to search node
        return Command(
            update={"next_action": "searching"},
            goto="search"
        )
    elif "calculate" in last_msg:
        return Command(
            update={"next_action": "calculating"},
            goto="calculate"
        )
    else:
        return Command(
            update={"next_action": "responding"},
            goto="respond"
        )

# Build graph - no need for add_conditional_edges!
builder = StateGraph(AgentState)
builder.add_node("router", router)
builder.add_node("search", search_node)
builder.add_node("calculate", calc_node)
builder.add_node("respond", respond_node)

builder.add_edge(START, "router")
# Command handles routing - just add edges from action nodes
builder.add_edge("search", END)
builder.add_edge("calculate", END)
builder.add_edge("respond", END)

app = builder.compile()
```

<Callout type="info">
  **Command vs Conditional Edges:** - Use **conditional edges** when routing
  logic is separate from state updates - Use **Command** when a node needs to
  update state AND control routing together - Command can also send messages to
  multiple nodes with `goto=["node1", "node2"]`
</Callout>
