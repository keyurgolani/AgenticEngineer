#### EX-01: First LLM Call

**Objective:** Make your first programmatic LLM call and observe the response.

```python
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0.7)
response = llm.invoke("Explain what an AI agent is in one sentence.")
print(response.content)
```

**Builds Toward:** Every agent in the capstone uses LLM calls.

<Callout type="tip">
**Acceptance Criteria:**
- Script executes without authentication errors
- Response object contains a non-empty `content` attribute
- Response is contextually relevant to the prompt (mentions agents, autonomy, or AI)
- Execution completes in under 10 seconds

**Expected Output:** A single sentence definition printed to console, e.g., `"An AI agent is an autonomous system that perceives its environment and takes actions to achieve specific goals."` The exact wording will vary due to temperature=0.7.

**Common Pitfalls:**

- Missing `OPENAI_API_KEY` environment variable — ensure it's exported or in `.env`
- Using `response` directly instead of `response.content` (prints the full AIMessage object)
- Rate limiting on new API keys — wait 60 seconds and retry
- Forgetting to install langchain-openai: `pip install langchain-openai`

**Extension Challenge:** Modify the script to accept user input via `input()`, make 3 consecutive calls with different prompts, and measure the average response time using `time.perf_counter()`. Print timing statistics at the end.

#### EX-02: Structured Output Parsing

**Objective:** Force an LLM to return JSON that matches a schema.

```python
from langchain_openai import ChatOpenAI
from pydantic import BaseModel, Field
from typing import List

class TaskAnalysis(BaseModel):
    task_type: str = Field(description="Type: research, code, creative, or general")
    complexity: str = Field(description="Complexity: low, medium, or high")
    keywords: List[str] = Field(description="Key terms from the request")

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)
structured_llm = llm.with_structured_output(TaskAnalysis)

result = structured_llm.invoke("Write a Python function to sort a list")
print(f"Type: {result.task_type}, Complexity: {result.complexity}")
```

**Builds Toward:** Request classification in the Orchestrator.

<Callout type="tip">
**Acceptance Criteria:**
- `result` is a valid `TaskAnalysis` instance (not a dict or string)
- `task_type` is one of: "research", "code", "creative", or "general"
- `complexity` is one of: "low", "medium", or "high"
- `keywords` is a non-empty list containing at least "Python" or "function" or "sort"
- No JSON parsing errors or validation exceptions

**Expected Output:** `Type: code, Complexity: low` (or medium). The keywords list should contain terms like `["Python", "function", "sort", "list"]`. Exact values may vary but must conform to the schema.

**Common Pitfalls:**

- Using `temperature > 0` can cause inconsistent field values — use `temperature=0` for classification
- Pydantic v1 vs v2 syntax differences — ensure you're using `from pydantic import BaseModel` (v2)
- Overly restrictive `Field` descriptions cause the LLM to fail validation — keep descriptions flexible
- Not handling `ValidationError` when the LLM returns malformed output in edge cases

**Extension Challenge:** Create a `BatchClassifier` that processes a list of 5 different task descriptions, returns all results, and calculates the distribution of task types. Add a `confidence: float` field to the schema and filter results where confidence < 0.7.

</Callout>

#### EX-03: Simple Tool Definition

**Objective:** Define a tool that an LLM can call.

```python
from langchain_core.tools import tool
from langchain_openai import ChatOpenAI

@tool
def get_word_count(text: str) -> int:
    """Count the number of words in the given text."""
    return len(text.split())

llm = ChatOpenAI(model="gpt-4o-mini")
llm_with_tools = llm.bind_tools([get_word_count])

response = llm_with_tools.invoke("Count words in: 'The quick brown fox'")
print(response.tool_calls)
```

**Builds Toward:** All agents use tools for external actions.

<Callout type="tip">
**Acceptance Criteria:**
- `response.tool_calls` is a non-empty list (length >= 1)
- First tool call has `name` equal to `"get_word_count"`
- Tool call `args` contains a `text` key with the input string
- The tool function itself returns `4` when invoked with "The quick brown fox"
- No exceptions during tool binding or invocation

**Expected Output:**

```python
[{'name': 'get_word_count', 'args': {'text': 'The quick brown fox'}, 'id': 'call_...', 'type': 'tool_call'}]
```

The `id` will be a unique identifier. The LLM decides to call the tool rather than answering directly.

**Common Pitfalls:**

- Missing docstring on the tool function — LLMs need the description to understand when to use it
- Forgetting to actually execute the tool after getting `tool_calls` — the LLM only _requests_ the call
- Type hints missing on tool parameters — causes schema generation to fail
- Using `@tool` without importing from `langchain_core.tools` (not `langchain.tools`)

**Extension Challenge:** Add a second tool `get_character_count(text: str) -> int` and modify the prompt to ask for both word and character counts. Implement a loop that executes all requested tool calls and prints their results. Handle the case where the LLM calls no tools.

</Callout>

#### EX-06: ReAct Loop (Single Iteration)

**Objective:** Implement one cycle of Reason, Act, Observe.

```python
from langchain_openai import ChatOpenAI
from langchain_core.tools import tool

@tool
def calculator(expression: str) -> str:
    """Evaluate a mathematical expression."""
    return str(eval(expression))

llm = ChatOpenAI(model="gpt-4o-mini")
llm_with_tools = llm.bind_tools([calculator])

response = llm_with_tools.invoke("What is 15% of 240?")
if response.tool_calls:
    result = calculator.invoke(response.tool_calls[0]['args'])
    print(f"Result: {result}")
```

**Builds Toward:** Agent execution loops in all specialized agents.

<Callout type="tip">
**Acceptance Criteria:**
- `response.tool_calls` contains at least one tool call for `calculator`
- Tool call args contain a valid mathematical expression (e.g., `"240 * 0.15"` or `"240 * 15 / 100"`)
- Executing the tool returns the correct result (`"36"` or `"36.0"`)
- The complete ReAct cycle (Reason → Act → Observe) executes without errors
- Result is printed to console with correct formatting

**Expected Output:**

```
Result: 36.0
```

The LLM reasons about the calculation, decides to use the calculator tool, and the result is computed and displayed.

**Common Pitfalls:**

- Using `eval()` in production — security risk! Use `ast.literal_eval()` or a safe math parser like `numexpr`
- Not checking if `tool_calls` is empty before accessing `[0]` — causes IndexError
- Forgetting to invoke the tool after getting the tool call — LLM only requests, doesn't execute
- Expression format varies by LLM — some return `"15% * 240"` which `eval()` can't parse
- Missing error handling for malformed expressions

**Extension Challenge:** Implement a full ReAct loop that continues until the LLM stops requesting tools. Add a `memory` tool that stores intermediate results, and solve a multi-step problem like "What is 15% of 240, then add 50, then divide by 2?" Track and display each reasoning step.

</Callout>

#### EX-07: Conversation Memory (In-Memory)

**Objective:** Maintain conversation context across multiple turns.

```python
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o-mini")
history = []

def chat(msg: str) -> str:
    history.append({"role": "user", "content": msg})
    response = llm.invoke(history)
    history.append({"role": "assistant", "content": response.content})
    return response.content

print(chat("My name is Alex."))
print(chat("What's my name?"))  # Should remember "Alex"
```

**Builds Toward:** Short-term memory in Memory Service.

<Callout type="tip">
**Acceptance Criteria:**
- First response acknowledges the name introduction appropriately
- Second response correctly recalls "Alex" from conversation history
- `history` list contains 4 entries after both exchanges (2 user + 2 assistant)
- Each history entry has correct `role` ("user" or "assistant") and non-empty `content`
- Memory persists across function calls within the same session

**Expected Output:**

```
Nice to meet you, Alex! How can I help you today?
Your name is Alex.
```

The exact wording varies, but the second response must contain "Alex" demonstrating memory retention.

**Common Pitfalls:**

- Using `response` instead of `response.content` when appending to history — stores AIMessage object, not string
- History growing unbounded — implement max length with sliding window (keep last N messages)
- Role format mismatch — some APIs expect `{"role": "user", "content": "..."}`, others expect HumanMessage objects
- Not handling empty responses — check `response.content` before appending
- Forgetting that history is global — multiple users would share memory (use session IDs in production)

**Extension Challenge:** Implement a `ConversationManager` class with: (1) session-based isolation using UUIDs, (2) configurable max history length with summarization of older messages, (3) a `clear()` method, and (4) persistence to a JSON file. Test with two interleaved conversations to verify isolation.

</Callout>

#### EX-08: Simple Router (If/Else)

**Objective:** Route requests to different handlers based on content.

```python
def classify_request(message: str) -> str:
    message_lower = message.lower()
    if any(kw in message_lower for kw in ["code", "function", "debug"]):
        return "code"
    elif any(kw in message_lower for kw in ["research", "find", "search"]):
        return "research"
    return "general"

# Test
print(classify_request("Write a Python function"))  # code
print(classify_request("Research AI trends"))       # research
```

**Builds Toward:** Smart Orchestrator request classification.

<Callout type="tip">
**Acceptance Criteria:**
- "Write a Python function" returns `"code"`
- "Research AI trends" returns `"research"`
- "Hello there" returns `"general"` (no matching keywords)
- Classification is case-insensitive ("WRITE CODE" → "code")
- Function handles empty strings without crashing (returns "general")

**Expected Output:**

```
code
research
```

The router correctly identifies the intent based on keyword matching.

**Common Pitfalls:**

- Case sensitivity — forgetting `.lower()` causes "Code" to not match "code"
- Keyword order matters — checking "code" before "research" means "research code patterns" routes to code
- Overlapping keywords — "find the code bug" matches both "find" (research) and "code" — first match wins
- Empty string handling — `"".lower()` works but ensure no index errors
- Hardcoded keywords don't scale — consider configuration file or database

**Extension Challenge:** Replace keyword matching with TF-IDF or embedding-based classification. Create a training set of 20 labeled examples (5 per category: code, research, general, creative), compute centroids for each category, and classify new requests by nearest centroid. Compare accuracy against the keyword approach.

#### EX-09: Embedding Generation

**Objective:** Generate vector embeddings for text.

```python
from sentence_transformers import SentenceTransformer
import numpy as np

model = SentenceTransformer("all-MiniLM-L6-v2")

texts = ["How do I write a Python function?", "Python function syntax"]
embeddings = model.encode(texts)

similarity = np.dot(embeddings[0], embeddings[1]) / (
    np.linalg.norm(embeddings[0]) * np.linalg.norm(embeddings[1])
)
print(f"Similarity: {similarity:.3f}")  # High similarity expected
```

**Builds Toward:** Semantic search in Memory and RAG services.

<Callout type="tip">
**Acceptance Criteria:**
- `embeddings` is a numpy array with shape `(2, 384)` — two texts, 384 dimensions each
- Similarity score is between 0.0 and 1.0 (cosine similarity range for normalized vectors)
- Similar texts ("Python function" queries) have similarity > 0.7
- Dissimilar texts ("Python function" vs "Italian cooking recipes") have similarity < 0.4
- Embedding generation completes in < 100ms for short texts on CPU

**Expected Output:**

```
Similarity: 0.847
```

The high similarity (> 0.8) indicates the two texts are semantically related (both about Python functions).

**Common Pitfalls:**

- First run downloads the model (~90MB) — can timeout in constrained environments
- Using wrong model name — `"all-MiniLM-L6-v2"` not `"all-minilm-l6-v2"` (case-sensitive)
- Not normalizing vectors before dot product — use the full cosine formula or `util.cos_sim()`
- GPU/CPU mismatch — model defaults to GPU if available, force CPU with `device='cpu'` if needed
- Memory issues with large batches — process in chunks of 32-64 texts

**Extension Challenge:** Build a `SemanticMatcher` class that: (1) pre-computes embeddings for a list of canonical categories, (2) classifies new text by finding the nearest category, (3) returns top-3 matches with scores, and (4) supports adding new categories at runtime. Test with 10 categories and 50 sample queries.

</Callout>

#### EX-11: Redis Basic Operations

**Objective:** Store and retrieve data from Redis.

```python
import redis
import json

r = redis.Redis(host='localhost', port=6379, decode_responses=True)

# Store conversation
session_id = "session_123"
r.rpush(f"messages:{session_id}", json.dumps({"role": "user", "content": "Hello"}))
r.expire(f"messages:{session_id}", 14400)  # 4 hour TTL

# Retrieve
messages = r.lrange(f"messages:{session_id}", 0, -1)
print([json.loads(m) for m in messages])
```

**Builds Toward:** Short-term memory storage.

<Callout type="tip">
**Acceptance Criteria:**

- `rpush` returns the new list length (1 after first push)
- `expire` returns `True` indicating TTL was set
- `lrange` returns all messages in insertion order
- Messages are valid JSON that can be parsed back to dicts
- Key expires after 4 hours (14400 seconds)

**Expected Output:**

```python
[{'role': 'user', 'content': 'Hello'}]
```

The message is stored and retrieved as a parsed Python dict.

**Common Pitfalls:**

- Redis not running — start with `docker run -p 6379:6379 redis:alpine` or `brew services start redis`
- Forgetting `decode_responses=True` — returns bytes instead of strings
- Not JSON-encoding before storage — `rpush` with dict fails, must use `json.dumps()`

- Key naming collisions — use namespaced keys like `app:messages:{session_id}`

#### EX-12: Document Chunking

**Objective:** Split a document into chunks for embedding.

```python
from langchain.text_splitter import RecursiveCharacterTextSplitter

text = """AI agents can use tools and maintain memory.
They work autonomously toward goals."""

splitter = RecursiveCharacterTextSplitter(chunk_size=50, chunk_overlap=10)
chunks = splitter.split_text(text)

for i, chunk in enumerate(chunks):
    print(f"Chunk {i}: {chunk}")
```

**Builds Toward:** Document processing in RAG service.

<Callout type="tip">
**Acceptance Criteria:**
- `chunks` is a non-empty list of strings
- Each chunk length is ≤ `chunk_size` (50 characters)
- Adjacent chunks have overlapping content (10 characters overlap)
- No content is lost — concatenating chunks (minus overlaps) reconstructs original
- Chunks split at natural boundaries (spaces, newlines) when possible

**Expected Output:**

```
Chunk 0: AI agents can use tools and maintain memory.
Chunk 1: maintain memory.
They work autonomously toward goals.
```

Note: Exact chunking depends on the splitter's boundary detection. Overlap ensures context continuity.

**Common Pitfalls:**

- `chunk_size` too small — creates many tiny chunks, loses context
- `chunk_overlap` >= `chunk_size` — causes infinite loop or duplicate content
- Not accounting for token count — character count ≠ token count for LLMs
- Splitting mid-word or mid-sentence — use `RecursiveCharacterTextSplitter` which prefers natural boundaries
- Forgetting metadata — chunks lose source document reference

**Extension Challenge:** Implement a `SmartChunker` that: (1) respects sentence boundaries using NLTK or spaCy, (2) preserves code blocks intact (don't split mid-function), (3) adds metadata (chunk_index, source_doc, char_range), (4) supports multiple strategies (fixed, semantic, paragraph-based). Test with a mixed document containing prose and code.

</Callout>

#### EX-13: Vector Store (ChromaDB)

```python
import chromadb
from sentence_transformers import SentenceTransformer

client = chromadb.Client()
```

**Builds Toward:** Vector storage in RAG service.

#### EX-14: Simple RAG Query

**Objective:** Answer a question using retrieved context.

```python
from langchain_openai import ChatOpenAI

# Assume we retrieved: "The company was founded in 2020 by Jane Smith."
context = "The company was founded in 2020 by Jane Smith."
```

### POC-01: LangGraph State Machine

**Time:** 1.5 hours | **Builds Toward:** Orchestrator, All Agents

**Objective:** Build a simple state machine using LangGraph that demonstrates state transitions and conditional routing.

```python
from typing import TypedDict, Literal
from langgraph.graph import StateGraph, END

class AgentState(TypedDict):
    message: str
    classification: str
    response: str

def classify_node(state: AgentState) -> dict:
    message = state["message"].lower()
    if "code" in message:
        return {"classification": "code"}
    elif "research" in message:
        return {"classification": "research"}
    return {"classification": "general"}

def code_node(state: AgentState) -> dict:
    return {"response": f"[CODE] {state['message']}"}

def research_node(state: AgentState) -> dict:
    return {"response": f"[RESEARCH] {state['message']}"}

def general_node(state: AgentState) -> dict:
    return {"response": f"[GENERAL] {state['message']}"}

def route(state: AgentState) -> Literal["code", "research", "general"]:
    return state["classification"]

workflow = StateGraph(AgentState)
workflow.add_node("classify", classify_node)
workflow.add_node("code", code_node)
workflow.add_node("research", research_node)
workflow.add_node("general", general_node)

workflow.set_entry_point("classify")
workflow.add_conditional_edges("classify", route)
workflow.add_edge("code", END)
workflow.add_edge("research", END)
workflow.add_edge("general", END)

app = workflow.compile()
result = app.invoke({"message": "Write Python code"})
print(result["response"])
```

**Validation:** Messages route to correct agent nodes based on classification.

<Callout type="info">
  **Technical Requirements:** LangGraph >= 0.2.0 with StateGraph support. Python
  3.11+ for TypedDict and Literal type hints. State must be immutable between
  node transitions (return new dict, don't mutate). All nodes must return
  partial state updates (only changed keys). Conditional edges must return valid
  node names as strings.
</Callout>

**Architecture Diagram Description:**

```
Entry → [classify] → (conditional) → [code|research|general] → END
                          ↓
         Route function inspects state["classification"]
         Returns string matching target node name
```

**Test Scenarios:**

2. Research request ("Find information about AI") → Routes to research node, response prefixed with `[RESEARCH]`
3. Ambiguous request ("Hello") → Routes to general node, response prefixed with `[GENERAL]`

5. Empty message → Graceful handling, routes to general without crash

**Success Metrics:**

- Classification accuracy ≥ 95% on clear requests
- State transitions complete in < 50ms (excluding LLM calls)
- Zero state mutation errors across 100 invocations
- Graph compiles without warnings

### POC-02: Semantic Memory Search

**Time:** 1.5 hours | **Builds Toward:** Memory Service, RAG Service

**Objective:** Implement semantic search over stored memories using embeddings.

```python
from sentence_transformers import SentenceTransformer
import numpy as np
from dataclasses import dataclass
from typing import List, Tuple

@dataclass
class Memory:
    content: str
    embedding: np.ndarray

class SemanticMemoryStore:
    def __init__(self):
        self.model = SentenceTransformer("all-MiniLM-L6-v2")
        self.memories: List[Memory] = []

    def store(self, content: str):
        embedding = self.model.encode(content)
        self.memories.append(Memory(content, embedding))

    def recall(self, query: str, top_k: int = 3) -> List[Tuple[str, float]]:
        query_emb = self.model.encode(query)
        results = []
        for mem in self.memories:
            sim = np.dot(query_emb, mem.embedding) / (
                np.linalg.norm(query_emb) * np.linalg.norm(mem.embedding)
            )
            results.append((mem.content, float(sim)))
        return sorted(results, key=lambda x: x[1], reverse=True)[:top_k]

store = SemanticMemoryStore()
store.store("User prefers Python over JavaScript")
store.store("User works on machine learning projects")
store.store("User's name is Alex")

results = store.recall("What programming language?")
for content, score in results:
    print(f"[{score:.3f}] {content}")
```

**Validation:** Similar queries retrieve related memories with high scores.

<Callout type="info">
  **Technical Requirements:** sentence-transformers >= 2.2.0 with
  `all-MiniLM-L6-v2` model (384-dim embeddings). NumPy for efficient vector
  operations (cosine similarity). Memory storage must support O(n) linear scan
  initially, O(log n) with indexing later. Embeddings must be normalized for
  consistent similarity scores (0.0 to 1.0 range). Thread-safe storage for
  concurrent read/write access.
</Callout>

**Architecture Diagram Description:**

```
[Store Operation]
Input Text → Embedding Model → Vector (384-dim) → Memory List

[Recall Operation]
Query Text → Embedding Model → Query Vector
                                    ↓
                            Cosine Similarity vs All Memories
                                    ↓
                            Sort by Score → Top-K Results
```

**Test Scenarios:**

1. Exact match query ("User prefers Python") → Returns matching memory with score > 0.9
2. Semantic match ("What language does user like?") → Returns Python preference with score > 0.7
3. Unrelated query ("What is the weather?") → All results have score < 0.5
4. Empty store recall → Returns empty list without error
5. Large store (1000+ memories) → Recall completes in < 500ms

**Success Metrics:**

- Semantic similarity correctly ranks related content (MRR@3 ≥ 0.8)
- Embedding generation < 50ms per text on CPU
- Memory footprint < 2KB per stored memory (content + embedding)
- Recall latency < 100ms for stores with < 1000 memories

**Production Considerations:**

### POC-03: Multi-Provider LLM Abstraction

**Time:** 2 hours | **Builds Toward:** LLM Router Service

**Objective:** Create a unified interface for multiple LLM providers with automatic fallback.

```python
from abc import ABC, abstractmethod
from typing import List, Dict
import os

class LLMProvider(ABC):
    @abstractmethod
    async def chat(self, messages: List[Dict]) -> str:
        pass

    @abstractmethod
    def is_available(self) -> bool:
        pass

class OpenAIProvider(LLMProvider):
    async def chat(self, messages: List[Dict]) -> str:
        from langchain_openai import ChatOpenAI
        llm = ChatOpenAI(model="gpt-4o-mini")
        response = await llm.ainvoke(messages)
        return response.content

    def is_available(self) -> bool:
        return bool(os.getenv("OPENAI_API_KEY"))

class UnifiedLLM:
    def __init__(self):
        self.providers = [OpenAIProvider()]

    async def chat(self, messages: List[Dict]) -> str:
        for provider in self.providers:
            if provider.is_available():
                try:
                    return await provider.chat(messages)
                except Exception:
                    continue
        raise RuntimeError("No providers available")
```

**Validation:** Fallback works when primary provider unavailable.

<Callout type="info">
**Technical Requirements:** Abstract base class with `@abstractmethod` for provider interface. Async-first design (`async def chat`) for non-blocking I/O. Provider availability check must be fast (< 10ms, no network calls). Support for at least 3 providers: OpenAI, Anthropic, local (Ollama). Unified message format compatible with OpenAI chat completion schema. Environment-based configuration for API keys and endpoints.
</Callout>

**Architecture Diagram Description:**

```
[UnifiedLLM]
     ↓
[Provider Registry] → [OpenAI] (priority: 1)
                    → [Anthropic] (priority: 2)
                    → [Ollama] (priority: 3, local fallback)
     ↓
For each provider (by priority):
  1. Check is_available()
  2. Try chat() with timeout
  3. On success → return response
  4. On failure → log error, try next provider
     ↓
All failed → raise RuntimeError
```

**Test Scenarios:**

### POC-04: Prompt Versioning System

**Time:** 1.5 hours | **Builds Toward:** Prompt Library Service

**Objective:** Implement prompt storage with version history and rollback.

```python
from dataclasses import dataclass, field
from datetime import datetime
from typing import Dict, List
import copy

@dataclass
class PromptVersion:
    version: int
    content: str
    created_at: datetime
    notes: str

@dataclass
class Prompt:
    name: str
    content: str
    version: int = 1
    versions: List[PromptVersion] = field(default_factory=list)

class PromptStore:
    def __init__(self):
        self.prompts: Dict[str, Prompt] = {}

    def create(self, name: str, content: str) -> Prompt:
        prompt = Prompt(name=name, content=content)
        prompt.versions.append(PromptVersion(1, content, datetime.now(), "Initial"))
        self.prompts[name] = prompt
        return prompt

    def update(self, name: str, content: str, notes: str = "") -> Prompt:
        prompt = self.prompts[name]
        prompt.version += 1
        prompt.content = content
        prompt.versions.append(PromptVersion(prompt.version, content, datetime.now(), notes))
        return prompt

    def rollback(self, name: str, to_version: int) -> Prompt:
        prompt = self.prompts[name]
        for v in prompt.versions:
            if v.version == to_version:
                return self.update(name, v.content, f"Rollback to v{to_version}")
        raise ValueError(f"Version {to_version} not found")
```

**Validation:** Versions increment, historical versions retrievable, rollback works.

<Callout type="info">
  **Technical Requirements:** Immutable version history (versions can never be
  deleted or modified). Version numbers must be monotonically increasing
  integers. Each version must capture: content, timestamp, author (if
  multi-user), change notes. Support Jinja2 template syntax for variable
  interpolation. Maximum 100 versions per prompt (configurable, with archival
  strategy). Thread-safe operations for concurrent access.
</Callout>

**Architecture Diagram Description:**

```
[PromptStore]
     ↓
[Prompt] ─────────────────────────────────────
  │ name: str                                 │
  │ content: str (current)                    │
  │ version: int (current)                    │
  │ versions: List[PromptVersion]             │
  └───────────────────────────────────────────┘
           ↓
[PromptVersion]
  │ version: int
  │ content: str
  │ created_at: datetime

```

**Test Scenarios:**

2. Update prompt 3 times → Version increments to 4, all versions in history
3. Rollback to version 2 → Creates version 5 with version 2's content, notes indicate rollback

5. Duplicate content update → Still creates new version (audit trail preserved)

**Success Metrics:**
