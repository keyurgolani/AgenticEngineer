<ConceptVisual
  image="/images/day_09_01_context_distraction_metaphor_1768860362350.png"
  alt="Visual metaphor showing the distraction caused by irrelevant context"
  caption="Irrelevant context acts like noise, drowning out the signal and reducing model performance."

<ConceptIntro
  title="Context Engineering"
  analogy="Imagine trying to solve a math problem while someone reads you random Wikipedia articles. The noise makes it harder to think. LLMs work the same way—if you fill their context window with irrelevant information, their 'IQ' drops. Context Engineering is the art of giving the model exactly what it needs, nothing more."
  technicalDef="Context Engineering is the set of strategies for curating and maintaining the optimal set of tokens during LLM inference. It goes beyond prompt engineering to include all information that enters the context: system prompts, tools, examples, message history, retrieved data, and runtime state. Building effective agents is less about finding the right words and more about answering: 'What configuration of context is most likely to generate our model's desired behavior?'"
  whyItMatters="Context is expensive (you pay per token) and limited (even 1M token windows fill up fast). Poor context management is the #1 cause of agent failures in production. Research shows that model performance degrades significantly as context length increases—even well below technical limits. As Anthropic's engineering team puts it: 'Context must be treated as a finite resource with diminishing marginal returns.'"
/>

<Callout type="tip">
  **Industry Shift:** As Andrej Karpathy noted: "People associate prompts with
  short task descriptions you'd give an LLM in your day-to-day use. When in
  every industrial-strength LLM app, context engineering is the delicate art and
  science of filling the context window with just the right information for the
  next step." This marks a fundamental shift from "prompt engineering" to
  "context engineering" in production AI systems.
</Callout>

### Context Engineering vs. Prompt Engineering

Understanding the distinction between these two disciplines is crucial:

| Aspect           | Prompt Engineering                 | Context Engineering                                           |
| :--------------- | :--------------------------------- | :------------------------------------------------------------ |
| **Focus**        | Writing effective instructions     | Curating the entire information environment                   |
| **Scope**        | The system prompt and user message | Everything: prompts, tools, examples, history, retrieved data |
| **Timing**       | One-time design                    | Iterative, every inference step                               |
| **Metaphor**     | Writing a recipe                   | Managing the kitchen during service                           |
| **Key Question** | "How do I phrase this?"            | "What information should the model see right now?"            |

<Callout type="info">
  **The Kitchen Analogy:** Prompt engineering is writing the recipe (static
  instructions). Context engineering is managing the kitchen during service
  (dynamic state). Before service starts, a chef has their station set: chopped
  onions, reduced sauces, and tools ready. During service, they dynamically
  manage what's on the counter based on incoming orders. Context engineering is
  that dynamic management—deciding what information is "on the counter" for each
  inference step.
</Callout>

<Callout type="info">
  **From Day 01:** Remember the ReAct loop (Reason → Act → Observe)? Each cycle
  adds to the context. A 50-step workflow with 20K tokens per call = 1M tokens
  total. Context accumulates across every LLM call, making management critical.
</Callout>

### The Attention Budget Problem

<ConceptVisual
  image="/images/day_09_02_attention_budget_flashlight_1768860382090.png"
  alt="Flashlight analogy showing attention dilution"
  caption="The Attention Budget: As context grows (wider beam), the intensity of attention on any single token diminishes."
/>

Here's a critical insight that surprises many engineers: **LLMs have a finite "attention budget" that gets depleted as context grows**.

<ConceptIntro
  title="The Attention Budget"
  analogy="Think of attention like a flashlight beam. A narrow beam illuminates one spot brightly. Spread that same light across a football field, and everything becomes dim. LLMs face the same tradeoff—the more tokens they must attend to, the less 'attention' each token receives."
  technicalDef="LLMs are based on the transformer architecture, where every token attends to every other token. This creates n² pairwise relationships for n tokens. As context length increases, the model's ability to capture these relationships gets stretched thin, creating a natural tension between context size and attention focus."
  whyItMatters="Every new token introduced depletes the attention budget. This is why thoughtful context curation—not just bigger context windows—is essential for building capable agents."
/>

### The Effective Context Window Problem

<ConceptVisual
  image="/images/day_09_03_context_window_chart_1768860406694.png"
  alt="Chart showing advertised vs effective context windows"
  caption="The Effective Context Window: Performance often degrades significantly before reaching the advertised token limit."
/>

The advertised context window is not the effective context window.

<RealWorldExample
  title="The NoLiMa Research Finding"
  scenario="Researchers tested 13 popular LLMs on long-context tasks using the NoLiMa benchmark, which removes literal keyword matching cues from needle-haystack tests."
  implementation="At 32K tokens, 11 out of 13 models dropped below 50% of their short-context performance. The models could technically process the tokens, but their accuracy plummeted when they couldn't rely on simple keyword matching."
  takeaway="Just because a model advertises 128K or 1M tokens doesn't mean it performs well at those lengths. The 'effective context window' where quality remains high is often 32K-64K tokens for most tasks."
/>

| Model Advertised Limit | Effective High-Quality Window | Performance at Full Context |
| :--------------------- | :---------------------------- | :-------------------------- |
| 128K tokens            | ~32K-64K tokens               | 40-60% of peak performance  |
| 200K tokens            | ~64K-100K tokens              | 50-70% of peak performance  |
| 1M tokens              | ~128K-256K tokens             | Varies significantly        |
| 2M tokens              | ~256K-512K tokens             | Task-dependent degradation  |

<Callout type="warning">
  **The "Lost in the Middle" Problem:** LLMs pay more attention to information
  at the beginning and end of the context. Information buried in the middle is
  often ignored or poorly recalled—performance can degrade by more than 30% when
  relevant information shifts from the edges to the middle. This is why
  strategic placement matters as much as content selection.
</Callout>

<ConceptVisual
  image="/images/day_09_04_attention_heatmap_1768860421288.png"
  alt="Heatmap showing attention distribution across context"
  caption="Lost in the Middle: Models pay most attention to the start and end of the context, with a significant performance dip in the middle."
/>

<Callout type="info">
  **Why This Happens:** Models develop attention patterns from training data
  where shorter sequences are more common. They have less experience with, and
  fewer specialized parameters for, context-wide dependencies. Techniques like
  position encoding interpolation help but introduce some degradation in token
  position understanding.
</Callout>

## 2.1 The Memory Hierarchy

<ConceptVisual
  image="/images/day_09_05_memory_hierarchy_diagram_1768860455758.png"
  alt="Agent Memory Hierarchy Diagram showing L1, L2, and L3 memory tiers"
  caption="The Agent Memory Hierarchy: Organizing context into hot (L1), warm (L2), and cold (L3) tiers."
/>

Just like a CPU has L1/L2/L3 cache, an agent needs a memory hierarchy. This maps directly to how you should think about context management.

<MemoryHierarchy />

<ConceptIntro
  title="The Memory Hierarchy"
  analogy="Think about how you remember things. Your working memory holds what you're thinking about right now (like a phone number you're about to dial). Your short-term memory holds recent events (what you had for breakfast). Your long-term memory holds facts and experiences (your childhood). Agents need all three types too."
  technicalDef="Agent memory is typically organized in tiers: L1 (Working Memory) is the current context window—fast but limited. L2 (Episodic Memory) stores past interactions in a vector database for retrieval. L3 (Archival Memory) holds compressed summaries and long-term facts."
  whyItMatters="You can't fit everything in the context window. A good memory hierarchy lets agents 'remember' relevant information without overwhelming the LLM or burning through your token budget."
/>

| Tier   | Type            | Technology      | Purpose                   | Speed     | Cost         | Typical Size  |
| :----- | :-------------- | :-------------- | :------------------------ | :-------- | :----------- | :------------ |
| **L1** | Working Memory  | Message List    | Immediate task context    | ⚡ Fast   | 💰 Expensive | 4K-32K tokens |
| **L2** | Episodic Memory | Vector Database | Relevant past experiences | 🔄 Medium | 💵 Moderate  | Unlimited     |
| **L3** | Archival Memory | Summaries/DB    | Long-term facts and goals | 🐢 Slow   | 💲 Cheap     | Unlimited     |

### How It Works in Practice

```
User: "What was that bug we fixed last month?"

1. L1 (Working Memory): Check current conversation → Not there
2. L2 (Episodic Memory): Search vector DB for "bug fix" → Found 3 relevant conversations
3. L3 (Archival Memory): Check summaries → "March: Fixed authentication timeout bug"

→ Agent retrieves the relevant context and responds accurately
```

### Context Budget Planning

<ConceptVisual
  image="/images/day_09_06_context_budget_pie_chart_1768860472126.png"
  alt="Pie chart showing optimal validation of a 32k context budget"
  caption="Budgeting Your Context: A typical production allocation reserves significant space for history and retrieved data while keeping the system prompt lean."
/>

Think of your context window as a budget that must be allocated:

```
Total Context Budget: 32,000 tokens (effective window)
├── System Prompt:        2,000 tokens (6%)
├── Tool Definitions:     3,000 tokens (9%)
├── Retrieved Context:    8,000 tokens (25%)
├── Conversation History: 12,000 tokens (38%)
├── Current User Input:   2,000 tokens (6%)
└── Reserved for Output:  5,000 tokens (16%)
```

<Callout type="tip">
  **Rule of Thumb:** Reserve 15-20% of your context budget for the model's
  output. If you fill the context completely with input, the model has no room
  to "think" and generate a quality response.
</Callout>

## 2.2 Pattern: Context Isolation (The "Sandboxing" Pattern)

<ConceptVisual
  image="/images/day_09_07_context_isolation_comparison_1768860492730.png"
  alt="Comparison of context pollution vs context isolation"
  caption="Context Isolation: Instead of sharing a massive, noisy context, give each agent only what it needs."
/>

<ConceptIntro
  title="Context Isolation"
  analogy="Imagine a company where every employee CC's everyone on every email. Soon, no one can find anything important—it's all buried in noise. Smart companies use 'need to know' principles: you only see information relevant to your job. Context Isolation applies the same principle to agents."
  technicalDef="Context Isolation means passing only the minimum viable context to each agent or sub-agent. In multi-agent systems, worker agents receive only their specific task and relevant results—not the entire conversation history or other agents' work. This follows the principle: 'Share memory by communicating, don't communicate by sharing memory.'"
  whyItMatters="Without isolation, agents get 'context poisoned'—confused by irrelevant information from other tasks. Isolation keeps each agent focused, reduces costs, and improves accuracy."
/>

**Problem:** In a multi-agent system, if every agent sees the entire conversation history, they get confused ("Context Pollution").

**Solution:** Pass only the _minimum viable context_ to a worker agent.

<Mermaid
  chart={`
sequenceDiagram
    participant User
    participant Supervisor
    participant Coder
    participant Researcher

    User->>Supervisor: "Build a stock app using value investing"
    Note over Supervisor: Breaks down the task

    Supervisor->>Researcher: [ISOLATED] "Find value investing formulas"
    Note over Researcher: Only sees this specific task
    Researcher-->>Supervisor: Returns: Formulas X, Y, Z

    Supervisor->>Coder: [ISOLATED] "Write Python func for Formula X"
    Note over Coder: Only sees formula, not research logs
    Coder-->>Supervisor: Returns: code.py

    Note over Supervisor: Combines results for user
    Supervisor-->>User: "Here's your stock app!"

`}
/>

### The Isolation Principle

| Aspect           | ❌ Without Isolation                                                                       | ✅ With Isolation                                                               |
| :--------------- | :----------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------ |
| **Context Size** | Coder sees: User request + Research logs + All formulas + Previous attempts (2,000 tokens) | Coder sees: "Write a Python function for Formula X: P/E ratio < 15" (50 tokens) |
| **Performance**  | Confused, slow, expensive                                                                  | Focused, fast, cheap                                                            |
| **Error Rate**   | High—model distracted by irrelevant info                                                   | Low—model focused on specific task                                              |
| **Cost**         | 40x more tokens = 40x more cost                                                            | Minimal token usage                                                             |

### When to Share vs. Isolate

| Scenario                                 | Recommendation                                                         |
| :--------------------------------------- | :--------------------------------------------------------------------- |
| Discrete task with clear input/output    | **Isolate**: Fresh context with only the specific instruction          |
| Complex reasoning requiring full history | **Share**: Pass relevant history when agent must understand trajectory |
| Debugging that needs previous attempts   | **Share**: Include error history so agent doesn't repeat mistakes      |
| Independent parallel tasks               | **Isolate**: Each sub-agent gets only its task                         |

## 2.3 Technique: Recursive Summarization

<ConceptVisual
  image="/images/day_09_08_recursive_summarization_funnel_1768860510957.png"
  alt="Process diagram of recursive summarization"
  caption="Recursive Summarization: Compressing history to maintain long-term context without blowing the budget."
/>

Don't just delete old messages. Compress them intelligently.

<ConceptIntro
  title="Recursive Summarization"
  analogy="Imagine reading a 500-page book and writing a 1-page summary. Then reading 10 such summaries and writing a 1-page summary of those. You've compressed 5,000 pages into 1 page while keeping the key information. Recursive Summarization does this for conversations."
  technicalDef="Recursive Summarization periodically compresses older messages into summaries. When the conversation exceeds a threshold (e.g., 20 turns), the oldest messages are summarized by an LLM and replaced with a single summary message. This can be applied recursively for very long conversations."
  whyItMatters="Long conversations fill up the context window. Without summarization, you either lose old context entirely or pay for tokens you don't need. Summarization preserves important information efficiently."
/>

### The Compression Hierarchy

Modern context engineering uses a hierarchy of compression techniques, preferring reversibility:

```
Preference Order (most to least preferred):
1. Raw Content      → Keep as-is (most accurate)
2. Compaction       → Remove redundant info that exists elsewhere (reversible)
3. Summarization    → LLM-generated summary (lossy but preserves meaning)
4. Deletion         → Remove entirely (last resort)
```

<Callout type="tip">
  **Compaction vs. Summarization:** Compaction removes information that can be
  retrieved later (e.g., "See file auth.py" instead of including the full file).
  Summarization condenses information that can't be easily retrieved. Prefer
  compaction when possible—it's reversible.
</Callout>

### How It Works

```
Before Summarization (20 messages, ~4000 tokens):
├── Message 1: User asks about project setup
├── Message 2: Agent explains options
├── Message 3: User chooses React
├── ... (messages 4-18)
├── Message 19: User asks about deployment
└── Message 20: Current question

After Summarization (11 messages, ~2000 tokens):
├── [SUMMARY]: "User is building a React app. Chose Tailwind for styling,
│              PostgreSQL for database. Completed: auth, dashboard.
│              Current focus: deployment to AWS."
├── Message 12-18: Recent context (kept in full)
├── Message 19: User asks about deployment
└── Message 20: Current question
```

### Implementation Pattern

```python
def maybe_summarize(messages: list, threshold: int = 20) -> list:
    """Summarize old messages if conversation is too long."""
    if len(messages) <= threshold:
        return messages

    # Take oldest messages to summarize (keep recent ones intact)
    to_summarize = messages[:threshold // 2]
    to_keep = messages[threshold // 2:]

    # Ask LLM to summarize—preserve key decisions and facts
    summary = llm.invoke(
        f"Summarize the key decisions, facts, and context from this conversation. "
        f"Preserve: user preferences, completed tasks, current goals, and any "
        f"constraints mentioned.\n\n{format_messages(to_summarize)}"
    )

    # Replace old messages with summary
    summary_message = {
        "role": "system",
        "content": f"[Previous conversation summary]: {summary}"
    }
    return [summary_message] + to_keep
```

<Callout type="warning">
  **Preserve Recent Tool Calls:** When summarizing, keep the most recent 2-3
  tool calls in their raw format. This maintains the model's "rhythm" and output
  formatting style, preventing quality degradation.
</Callout>

## 2.4 The Four Pillars of Context Engineering

<ConceptVisual
  image="/images/day_09_09_four_pillars_diagram_1768860547586.png"
  alt="The Four Pillars of Context Engineering"
  caption="The Context Architecture: Write, Select, Compress, and Isolate."
/>

Based on industry best practices, here's a comprehensive framework for managing context:

<Mermaid
  chart={`
graph TB
    subgraph "The Four Pillars"
        Write[📝 1. Write<br/>Persist externally] --> Select[🎯 2. Select<br/>Retrieve relevant]
        Select --> Compress[🗜️ 3. Compress<br/>Reduce tokens]
        Compress --> Isolate[🔒 4. Isolate<br/>Scope per agent]
    end
    
    Write -.-> |"Scratchpad, artifacts"| DB[(External Storage)]
    Select -.-> |"Vector search, recency"| DB
    Compress -.-> |"Summarize, compact"| DB
    Isolate -.-> |"Filter per task"| Output[✨ Optimized Context]
`}
/>

### 1. Write (Persist Outside the Prompt)

Store information externally so you can retrieve it later without keeping it in context:

| What to Write        | Where to Store           | When to Retrieve           |
| :------------------- | :----------------------- | :------------------------- |
| **Scratchpad**       | Key-value store          | During current task        |
| **Artifacts**        | File system/blob storage | When referenced            |
| **Facts learned**    | Vector database          | When semantically relevant |
| **User preferences** | User profile DB          | At session start           |

### 2. Select (Retrieve Only What Matters)

Don't include everything—retrieve based on relevance using multiple signals:

```python
def select_context(query: str, conversation: list, tools: list) -> dict:
    """Select relevant context using multiple retrieval strategies."""
    return {
        # Recency: Last 3-5 turns are almost always relevant
        "recent_messages": conversation[-5:],

        # Semantic: Vector search for related past experiences
        "relevant_history": vector_db.search(query, k=3),

        # Task-specific: Only tools likely needed for this query
        "active_tools": filter_tools_by_relevance(tools, query),

        # User context: Preferences and constraints
        "user_context": get_user_preferences(user_id),
    }
```

### 3. Compress (Fight Token Bloat)

Reduce token usage without losing critical information:

| Technique     | When to Use                                         | Token Savings |
| :------------ | :-------------------------------------------------- | :------------ |
| **Prune**     | Remove irrelevant sentences                         | 20-40%        |
| **Compact**   | Replace outputs with pointers ("See artifact #123") | 50-80%        |
| **Summarize** | Distill to key points                               | 60-90%        |
| **Truncate**  | Cut off at token limit (last resort)                | Variable      |

### 4. Isolate (Prevent Collisions)

Keep contexts separate to prevent pollution:

- **Per-agent isolation**: Each sub-agent gets only its task
- **Per-user isolation**: User-specific context stays with that user
- **Per-task isolation**: Debug info stays out of production prompts
- **Temporal isolation**: Old context doesn't pollute new tasks

## 2.5 Just-in-Time Context Retrieval

<ConceptVisual
  image="/images/day_09_11_jit_context_analogy_1768860583973.png"
  alt="Comparison of preloaded vs just-in-time context strategies"
  caption="Just-in-Time Context: Dynamic retrieval beats trying to memorize everything upfront."
/>

<ConceptIntro
  title="Just-in-Time Context"
  analogy="Imagine a researcher who memorizes entire libraries before answering any question versus one who knows how to quickly find and retrieve exactly what they need. The second researcher is faster, more accurate, and can handle a much wider range of questions. Just-in-Time retrieval gives agents this same capability."
  technicalDef="Just-in-Time (JIT) context retrieval is a strategy where agents maintain lightweight identifiers (file paths, stored queries, web links) and use tools to dynamically load data into context at runtime, rather than pre-loading all potentially relevant information upfront."
  whyItMatters="JIT retrieval enables progressive disclosure—agents incrementally discover relevant context through exploration. Each interaction yields context that informs the next decision, keeping the agent focused on relevant subsets rather than drowning in exhaustive but potentially irrelevant information."
/>

### Preloaded vs. Just-in-Time vs. Hybrid

<Mermaid
  chart={`
graph LR
    subgraph "Preloaded (Traditional)"
        P1[User Query] --> P2[Load ALL<br/>Relevant Docs]
        P2 --> P3[Send to LLM]
        P3 --> P4[Response]
    end
    
    subgraph "Just-in-Time (Modern)"
        J1[User Query] --> J2[LLM Decides<br/>What's Needed]
        J2 --> J3[Retrieve<br/>Specific Data]
        J3 --> J4[Continue<br/>Reasoning]
    end
    
    subgraph "Hybrid (Best Practice)"
        H1[User Query] --> H2[Load Minimal<br/>Essential Context]
        H2 --> H3[LLM Reasons]
        H3 --> H4[Retrieve<br/>As Needed]
        H4 --> H5[Continue]
    end
`}
/>

| Approach         | Pros                          | Cons                              | Best For                      |
| :--------------- | :---------------------------- | :-------------------------------- | :---------------------------- |
| **Preloaded**    | Simple, everything available  | Wastes tokens, causes pollution   | Small, static knowledge bases |
| **Just-in-Time** | Efficient, focused, scales    | Slower, requires good tool design | Large, dynamic environments   |
| **Hybrid**       | Balanced speed and efficiency | More complex to implement         | Most production agents        |

### How Claude Code Uses Hybrid Context

Anthropic's Claude Code demonstrates the hybrid approach effectively:

```python
# Hybrid context strategy example
def hybrid_context_approach(query: str, workspace: str) -> dict:
    """
    Hybrid approach: minimal preload + just-in-time retrieval.
    Based on patterns from Claude Code.
    """
    # PRELOAD: Essential, always-needed context (loaded upfront)
    initial_context = {
        "system_prompt": get_system_prompt(),
        "project_config": load_file("CLAUDE.md"),  # Project-specific instructions
        "recent_messages": get_recent_messages(limit=3),
    }

    # JUST-IN-TIME: Tools for retrieving additional context on demand
    retrieval_tools = [
        {
            "name": "glob",
            "description": "Find files matching a pattern"
        },
        {
            "name": "grep",
            "description": "Search file contents for patterns"
        },
        {
            "name": "read_file",
            "description": "Read specific file contents"
        },
        {
            "name": "head_tail",
            "description": "Preview start/end of large files"
        },
    ]

    return {
        "context": initial_context,
        "tools": retrieval_tools,
        "strategy": "Agent retrieves additional context as needed"
    }
```

<Callout type="tip">
  **Progressive Disclosure:** Let agents navigate and retrieve data
  autonomously. File sizes suggest complexity, naming conventions hint at
  purpose, timestamps indicate relevance. Agents can assemble understanding
  layer by layer, maintaining only what's necessary in working memory.
</Callout>

### When to Preload vs. Retrieve Just-in-Time

| Information Type      | Strategy | Rationale                          |
| :-------------------- | :------- | :--------------------------------- |
| System instructions   | Preload  | Always needed, rarely changes      |
| User preferences      | Preload  | Essential for personalization      |
| Project configuration | Preload  | Defines agent behavior             |
| Recent conversation   | Preload  | Immediate context                  |
| Large codebases       | JIT      | Too large, retrieve relevant files |
| Documentation         | JIT      | Search when needed                 |
| Historical data       | JIT      | Retrieve based on relevance        |
| Tool outputs          | JIT      | Generate and retrieve on demand    |

## 2.6 Detecting and Fixing Context Problems

<ConceptVisual
  image="/images/day_09_12_context_health_dashboard_1768860603524.png"
  alt="Dashboard showing metrics for monitoring context health"
  caption="Monitor Your Context: Watch for token bloat, high repetition, and confusion signals."

### Signs of Context Rot

<Callout type="warning">
  **Warning Signs Your Context is Rotting:** - Agent starts forgetting earlier
  instructions - Responses become generic or off-topic - Agent confuses
  different users or tasks - Quality degrades as conversations get longer -
  Agent repeats itself or contradicts earlier statements - Tool calls become
  less accurate or use wrong parameters
</Callout>

### The Three Context Failure Modes

| Failure Mode            | Symptoms                                         | Fix                                               |
| :---------------------- | :----------------------------------------------- | :------------------------------------------------ |
| **Context Rot**         | Performance degrades with length                 | Summarize, compress, or start fresh               |
| **Context Pollution**   | Irrelevant info distracts model                  | Filter aggressively, isolate contexts             |
| **Context Confusion**   | Conflicting instructions                         | Consolidate system prompts, remove contradictions |
| **Context Distraction** | Model over-focuses on context, ignoring training | Reduce context size, prioritize relevance         |

### Debugging Context Issues

```python
def debug_context(messages: list) -> dict:
    """Analyze context for potential issues."""
    total_tokens = count_tokens(messages)

    issues = []

    # Check for size issues
    if total_tokens > 50000:
        issues.append("⚠️ Context very large—consider summarization")

    # Check for repetition (pollution indicator)
    contents = [m['content'] for m in messages]
    unique_ratio = len(set(contents)) / len(contents)
    if unique_ratio < 0.8:
        issues.append("⚠️ High repetition detected—prune duplicates")

    # Check for multiple system messages (confusion risk)
    system_msgs = [m for m in messages if m['role'] == 'system']
    if len(system_msgs) > 3:
        issues.append("⚠️ Multiple system messages—consolidate to prevent confusion")

    # Check for very old messages (rot indicator)
    if len(messages) > 30:
        issues.append("⚠️ Long conversation—consider summarizing older turns")

    return {
        "total_tokens": total_tokens,
        "message_count": len(messages),
        "avg_tokens_per_message": total_tokens // len(messages),
        "unique_content_ratio": unique_ratio,
        "system_message_count": len(system_msgs),
        "issues": issues,
    }
```

## 2.8 RAG vs. Long Context: When to Use Each

<ConceptVisual
  image="/images/day_09_14_rag_vs_long_context_1768860665420.png"
  alt="Decision matrix comparing RAG vs Long Context"
  caption="RAG vs. Long Context: Use RAG for precision and scale; use Long Context for deep reasoning."
/>

With context windows expanding to 1M+ tokens, a common question is: "Is RAG still necessary?" The answer is nuanced.

<ConceptIntro
  title="RAG vs. Long Context"
  analogy="Imagine you need to answer questions about a library's entire collection. Long context is like having photographic memory of every book—impressive, but you still get confused with too much information. RAG is like having a skilled librarian who fetches exactly the books you need. Both have their place."
  technicalDef="RAG (Retrieval-Augmented Generation) retrieves relevant chunks from external storage and injects them into context. Long context approaches load large amounts of data directly into the context window. The choice depends on data size, update frequency, accuracy requirements, and cost constraints."
  whyItMatters="Choosing the wrong approach can result in 10-80x higher costs, degraded accuracy, or both. Understanding the tradeoffs is essential for production systems."
/>

### The Tradeoff Matrix

| Factor         | RAG                                 | Long Context                 |
| :------------- | :---------------------------------- | :--------------------------- |
| **Cost**       | 8-82x cheaper for typical workloads | Expensive at scale           |
| **Latency**    | Fast retrieval, smaller inference   | Slower with large contexts   |
| **Accuracy**   | High precision on retrieved chunks  | Degrades with context length |
| **Freshness**  | Can update index in real-time       | Requires re-processing       |
| **Complexity** | Requires retrieval infrastructure   | Simpler architecture         |
| **Best For**   | Large, dynamic knowledge bases      | Small, static documents      |

### Decision Framework

```
┌─────────────────────────────────────────────────────────────┐
│                    RAG vs. Long Context                      │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  Data Size > 100K tokens?                                    │
│    YES → Lean toward RAG                                     │
│    NO  → Long context may work                               │
│                                                              │
│  Data updates frequently?                                    │
│    YES → RAG (easier to update index)                        │
│    NO  → Either approach works                               │
│                                                              │
│  Need high precision on specific facts?                      │
│    YES → RAG (focused retrieval)                             │
│    NO  → Long context acceptable                             │
│                                                              │
│  Cost-sensitive at scale?                                    │
│    YES → RAG (much cheaper)                                  │
│    NO  → Long context for simplicity                         │
│                                                              │
│  Need to reason across entire corpus?                        │
│    YES → Long context or hybrid                              │
│    NO  → RAG sufficient                                      │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

### The Hybrid Approach (Recommended)

Most production systems benefit from combining both approaches:

```python
def hybrid_retrieval(query: str, corpus: str, config: dict) -> dict:
    """
    Hybrid RAG + Long Context approach.
    Use RAG for precision, long context for reasoning.
    """
    # Step 1: Always include essential context (long context)
    base_context = {
        "system_prompt": config["system_prompt"],
        "schema_definitions": config["schemas"],  # Always needed
        "recent_conversation": get_recent_messages(5),
    }

    # Step 2: Retrieve relevant chunks (RAG)
    relevant_chunks = vector_db.search(
        query=query,
        k=config.get("retrieval_k", 5),
        threshold=config.get("similarity_threshold", 0.7)
    )

    # Step 3: Optionally load full documents for deep reasoning
    if requires_deep_reasoning(query):
        # Load full documents for chunks that scored highly
        full_docs = [load_full_document(chunk.doc_id)
                     for chunk in relevant_chunks[:2]]
        base_context["full_documents"] = full_docs

    # Step 4: Assemble final context within budget
    return assemble_context(
        base=base_context,
        retrieved=relevant_chunks,
        budget=config.get("context_budget", 32000)
    )
```

<Callout type="warning">
  **RAG is Not Dead:** Despite claims that large context windows make RAG
  obsolete, research shows RAG remains 8-82x cheaper and often more accurate.
  Bigger windows add cost and noise; retrieval focuses attention where it
  matters. The question isn't "RAG or long context?" but "How do I combine them
  effectively?"
</Callout>

### The Two Failure Modes of Long-Running Agents

Based on Anthropic's research building the Claude Agent SDK:

| Failure Mode             | Description                           | Consequence                                                         |
| :----------------------- | :------------------------------------ | :------------------------------------------------------------------ |

The key insight is finding a way for agents to quickly understand the state of work when starting with a fresh context window:

{chr(10).join(f'{i+1}. {step}' for i, step in enumerate(next_steps))}

### Compaction: Intelligent Context Compression

Compaction is the practice of summarizing a conversation nearing the context limit and reinitiating with the summary. It's typically the first lever for driving better long-term coherence.

```python
def compact_context(messages: list, model: str = "claude-sonnet") -> dict:
    """
    Compaction strategy based on Anthropic's Claude Code approach.
    Preserves critical details while discarding redundant information.
    """
    # Identify what to preserve vs. discard
    preserve_categories = [
        "architectural_decisions",
        "unresolved_bugs",
        "implementation_details",
        "user_preferences",
        "current_goals"
    ]

    discard_categories = [
        "redundant_tool_outputs",
        "superseded_messages",
        "verbose_intermediate_steps"

    # Generate high-fidelity summary
    summary = llm.invoke(f"""
    Summarize this conversation, preserving:
    - Architectural decisions made
    - Unresolved bugs or issues
    - Key implementation details
    - User preferences and constraints
    - Current goals and next steps

    Discard:
    - Redundant tool outputs
    - Superseded or corrected information

class AgenticMemory:
    """
    Structured note-taking system for long-horizon agents.
    Based on patterns from Anthropic's research.
    """
    def __init__(self, memory_file: str = "NOTES.md"):
        self.memory_file = memory_file

    def write_note(self, category: str, content: str):
        """Write a structured note to persistent memory."""
        timestamp = datetime.now().isoformat()
        note = f"\n## [{category}] {timestamp}\n{content}\n"

        with open(self.memory_file, "a") as f:
            f.write(note)

    def read_notes(self, category: str = None) -> str:
        """Retrieve notes, optionally filtered by category."""
        with open(self.memory_file, "r") as f:
            notes = f.read()

        if category:
            # Filter to specific category
            return self._filter_by_category(notes, category)
        return notes

    def update_todo(self, completed: list, remaining: list):
        """Update the running to-do list."""
        self.write_note("TODO", f"""
Completed:
{chr(10).join(f'- [x] {item}' for item in completed)}

Remaining:
{chr(10).join(f'- [ ] {item}' for item in remaining)}
        """)
```

```python
# ❌ Bad: Include all 50 tools in every call
tools = get_all_tools()  # 50 tools × 200 tokens = 10,000 tokens

# ✅ Good: Dynamically select relevant tools
def get_relevant_tools(query: str, all_tools: list, max_tools: int = 10) -> list:
    """Select only tools likely needed for this query."""
    # Use embeddings to find semantically relevant tools
    tool_scores = []
    query_embedding = embed(query)

    for tool in all_tools:
        tool_embedding = embed(tool['description'])
        score = cosine_similarity(query_embedding, tool_embedding)
        tool_scores.append((tool, score))

    # Return top-k most relevant tools
    tool_scores.sort(key=lambda x: x[1], reverse=True)
    return [t[0] for t in tool_scores[:max_tools]]
```

<DeepDive title="Advanced: Just-in-Time vs. Preloaded Context">

Modern agent architectures increasingly favor **just-in-time retrieval** over preloading context:

**Preloaded Context (Traditional)**

```
User query → Load all potentially relevant docs → Send to LLM → Response
```

- Pros: Simple, everything available
- Cons: Wastes tokens, causes pollution, hits context limits

**Just-in-Time Retrieval (Modern)**

```
User query → LLM decides what info needed → Retrieve specific docs → Continue reasoning
```

- Pros: Efficient, focused, scales better
- Cons: More complex, requires good tool design

**Hybrid Approach (Best Practice)**

```
User query → Load minimal essential context → LLM reasons → Retrieve as needed → Continue
```

The key insight: let the agent decide what context it needs rather than front-loading everything "just in case."

**Implementation Pattern:**

```python
def hybrid_context_approach(query: str, user_context: dict) -> dict:
    """Hybrid approach: minimal preload + just-in-time retrieval."""
    # Preload: Only essential, always-needed context
    initial_context = {
        "system_prompt": get_system_prompt(),
        "user_preferences": user_context.get("preferences", {}),
        "recent_messages": get_recent_messages(limit=3),
    }

    # Just-in-time: Tools for retrieving additional context
    retrieval_tools = [
        {"name": "search_docs", "description": "Search documentation"},
        {"name": "get_file", "description": "Retrieve specific file contents"},
        {"name": "query_history", "description": "Search conversation history"},
    ]

    return {
        "context": initial_context,
        "tools": retrieval_tools,
        "strategy": "Agent retrieves additional context as needed"
    }
```
