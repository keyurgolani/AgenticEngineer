## Why Document Agents?

As agents become more complex and numerous, we need a standard way to describe what they can do. The `AGENTS.md` file serves as a "user manual" that both humans and other AI systems can understand.

> **Key Insight**: A well-documented agent is a trustworthy agent. Clear boundaries and capabilities build confidence.

The problem before AGENTS.md was fragmentation. Different tools required different configuration files: `.cursorrules` for Cursor, `CLAUDE.md` for Claude, `.gemini/settings.json` for Gemini CLI. Developers juggled multiple redundant files that all needed separate updates.

AGENTS.md emerged as the unified solution—a single, predictable location where any AI coding agent can find the instructions it needs.

Here's a production-ready template that incorporates lessons from analyzing thousands of repositories:

```markdown
# Research Assistant Agent

## Overview

An AI agent specialized in conducting research on technical topics,

## Version

- Agent Version: 2.1.0
- Last Updated: 2025-01-15
- Maintainer: engineering@company.com
- Changelog: See CHANGELOG.md

## Tech Stack

- **Framework**: LangGraph 0.2.x
- **LLM**: GPT-4o (primary), Claude 3.5 Sonnet (fallback)
- **Vector DB**: ChromaDB
- **Search**: Tavily API
- **Language**: Python 3.11+
```

## Capabilities

### Core Functions

- [x] Web search and information retrieval
- [x] Document summarization
- [x] Multi-source synthesis
- [x] Citation generation
- [x] Structured report writing

### Tools Available

| Tool         | Description               | Rate Limit |
| :----------- | :------------------------ | :--------- |
| `web_search` | Search the web via Tavily | 100/hour   |
| `read_url`   | Fetch and parse web pages | 50/hour    |
| `summarize`  | Summarize long documents  | No limit   |
| `cite`       | Generate citations        | No limit   |

### Data Access

- Public web content
- Company knowledge base (read-only)
- Research paper databases (via API)

## Limitations

### Cannot Do

- Access private/authenticated websites
- Modify any databases or files
- Execute arbitrary code
- Access real-time data (stock prices, etc.)
- Process images or videos

### Known Issues

- May struggle with highly technical jargon in niche fields
- Citation format may need manual verification
- Rate limits may cause delays on large research tasks

### Boundaries

- Maximum report length: 5,000 words
- Maximum sources per report: 20
- Timeout: 10 minutes per research task

## Security

### Authentication

- Requires valid API key in `X-Agent-Key` header
- Rate limited to 100 requests/day per key
- Keys rotate every 90 days

### Permission Boundaries

| Resource       | Permission | Notes            |
| :------------- | :--------- | :--------------- |
| Web URLs       | Read       | Public only      |
| Knowledge Base | Read       | No PII access    |
| File System    | None       | Sandboxed        |
| Databases      | None       | No direct access |
| Credentials    | None       | Never exposed    |

### Audit Trail

- All requests logged with timestamp, user, action
- Logs retained for 90 days
- Available via `/audit` endpoint

## Usage

<Callout type="success">
  **Key Finding:** The analysis showed a clear pattern: provide your agent a
  specific job or persona, exact commands to run, well-defined boundaries to

### What Works

1. **Specific Tech Stack Versions**

   ```markdown
   ## Tech Stack

   - React 18.2.0
   - TypeScript 5.3
   - Node.js 20 LTS
   ```

   Not just "React" but the specific version. Agents need precision.

2. **Executable Commands with Exact Flags**

   ```markdown
   ## Commands

   - `pnpm install --filter PROJECT_NAME` - Install deps for package
   - `pnpm turbo run test --filter PROJECT_NAME` - Run package tests
   - `pnpm vitest run -t "TEST_NAME"` - Run specific test
   ```

3. **Clear Boundaries with Explicit Prohibitions**

   ```markdown
   ## Do NOT

   - Modify package.json without approval
   - Delete test files
   - Change authentication logic
   - Commit directly to main branch
   - Rotate API keys without notifying security
   ```

4. **Testing Procedures with Success Criteria**

   ```markdown
   ## Testing

   1. Run `npm test` before committing
   2. Ensure coverage > 80%
   3. All E2E tests must pass
   4. Fix any test or type errors until suite is green
   5. Add tests for code you change, even if nobody asked
   ```

5. **PR and Commit Guidelines**

   ```markdown
   ## PR Instructions

   - Title format: [PROJECT_NAME] Title
   - Always run `pnpm lint` and `pnpm test` before committing
   - Include test coverage report in PR description
   ```

### What Doesn't Work

| Anti-Pattern                        | Why It Fails                              | Better Approach                                          |
| :---------------------------------- | :---------------------------------------- | :------------------------------------------------------- |
| Vague descriptions ("handles data") | Agent can't determine actual capabilities | "Queries PostgreSQL with read-only access, max 10k rows" |
| Missing version information         | Can't tell if docs match current agent    | Include agent version, last updated, framework versions  |
| No examples                         | Users guess at input format               | Provide 2+ examples with actual input/output             |
| Only capabilities, no limitations   | Users attempt impossible tasks            | Explicitly list what agent CANNOT do                     |
| Abstract guidelines                 | Agent can't execute them                  | Use concrete, copy-pasteable commands                    |

**Precedence order (later overrides earlier):**

1. **Global scope**: `~/.codex/AGENTS.md` - Your personal defaults
2. **Project root**: `/repo/AGENTS.md` - Repository-wide rules
3. **Subdirectories**: Nested AGENTS.md files along the path
4. **Override files**: `AGENTS.override.md` takes precedence at any level

### Example: Global Defaults

Create persistent defaults that every repository inherits:

```markdown
# ~/.codex/AGENTS.md

## Working Agreements

- Always run `npm test` after modifying JavaScript files
- Prefer `pnpm` when installing dependencies
- Ask for confirmation before adding new production dependencies
- Never commit secrets or API keys
- Use conventional commit messages
```

### Example: Project Override

```markdown
# /repo/services/payments/AGENTS.override.md

## Payments Service Rules

- Use `make test-payments` instead of `npm test`
- Never rotate API keys without notifying #security channel
- All changes require security review
- PCI compliance: no logging of card data
```

<Callout type="warning">
  **Size Limits:** Codex stops adding files once combined size reaches 32 KiB by
  default. For larger instruction sets, split across nested directories or
  increase `project_doc_max_bytes` in your config.
</Callout>

### Security Section Template

```markdown

### Authentication & Authorization

- Agent authenticates via service account `agent-prod@company.iam`
- Scoped to `read:repos`, `write:issues` permissions only
- No access to admin endpoints
```

### Network Boundaries

| Destination             | Allowed        | Protocol |
| :---------------------- | :------------- | :------- |
| api.company.com         | Yes            | HTTPS    |
| \*.internal.company.com | Yes            | HTTPS    |
| External APIs           | Allowlist only | HTTPS    |
| Raw IP addresses        | No             | -        |

### Data Handling

- PII: Never log, never store, mask in outputs
- Credentials: Never echo, never include in responses
- User data: Process in memory only, no persistence
- Audit: All actions logged to security SIEM

### Prohibited Actions

- Executing shell commands outside sandbox
- Accessing environment variables directly
- Making requests to non-allowlisted domains
- Storing user data beyond session
- Bypassing rate limits via any method

````
### Agent Registry Pattern

```python
import yaml
import re
from pathlib import Path

class AgentRegistry:
    def __init__(self):
        self.agents = {}

    def register_from_agents_md(self, path: Path):
        """Parse AGENTS.md and register agent metadata."""
        content = path.read_text()

        # Extract metadata from HTML comment
        match = re.search(
            r'<!--\s*AGENT_METADATA\s*(.*?)\s*-->',
            content,
            re.DOTALL
        )

        if match:
            metadata = yaml.safe_load(match.group(1))
            self.agents[metadata['name']] = {
                'metadata': metadata,
                'path': path,
                'capabilities': metadata.get('capabilities', []),
                'tags': metadata.get('discovery', {}).get('tags', [])
            }
````

    def find_by_capability(self, capability: str) -> list:
        """Find all agents with a specific capability."""
        return [
            agent for agent in self.agents.values()
            if capability in agent['capabilities']
        ]

    def find_by_tag(self, tag: str) -> list:
        """Find all agents matching a tag."""
        return [
            agent for agent in self.agents.values()
            if tag in agent['tags']
        ]

# Usage

registry = AgentRegistry()
registry.register_from_agents_md(Path("agents/research/AGENTS.md"))
registry.register_from_agents_md(Path("agents/code/AGENTS.md"))

# Find agent for research task

research_agents = registry.find_by_capability("web_search")


| **goose**     | Vendor-neutral agent framework          | Reference implementation | Apache 2.0       |

<Callout type="info">
  **Complementary Standards:** AGENTS.md documents *what* an agent can do. MCP
  defines *how* it connects to tools. A2A defines *how* agents talk to each
  other. A well-architected system uses all three together.
</Callout>

## 12.10 Versioning Your Agent Documentation

As your agent evolves, your documentation must evolve with it. Here's how to version AGENTS.md effectively:

### Semantic Versioning for Agents

```markdown
## Version

- **Agent Version**: 2.1.0
- **AGENTS.md Version**: 2.1.0 (keep in sync)
- **Last Updated**: 2025-01-15
- **Breaking Changes Since**: 2.0.0

### Version History

| Version | Date       | Changes                          |
| :------ | :--------- | :------------------------------- |
| 2.1.0   | 2025-01-15 | Added comprehensive depth option |
| 2.0.0   | 2025-11-15 | Breaking: New request format     |
| 1.5.0   | 2025-09-01 | Added citation tool              |
```

### When to Update

- **Patch (2.1.x)**: Documentation fixes, clarifications
- **Minor (2.x.0)**: New capabilities, new tools, expanded access
- **Major (x.0.0)**: Breaking changes to input/output schemas, removed capabilities

## 12.11 Migrating to AGENTS.md

If you have existing agent configuration files, migration is straightforward:

```bash
# Rename your primary file
mv AGENT.md AGENTS.md

# Create symbolic link for backward compatibility
ln -s AGENTS.md AGENT.md

# For Cursor users
ln -s AGENTS.md .cursorrules

# For Claude users
ln -s AGENTS.md CLAUDE.md
```

### Tool-Specific Configuration

Some tools need additional configuration to recognize AGENTS.md:

**Aider** (`.aider.conf.yml`):

```yaml
read: AGENTS.md
```

**Gemini CLI** (`.gemini/settings.json`):

```json
{
  "contextFileName": "AGENTS.md"
}
```

**OpenAI Codex** (`~/.codex/config.toml`):

```toml
# Add fallback filenames if using legacy names
project_doc_fallback_filenames = ["TEAM_GUIDE.md", ".agents.md"]
project_doc_max_bytes = 65536
```
